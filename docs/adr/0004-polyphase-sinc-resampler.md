# 0004. `rubato` を自前のポリフェーズ窓付き sinc リサンプラへ置き換える —— 窓・タップ数・遅延の選定

## 状態

採用

## 日付

2026-09-30

## 文脈

依存排除計画(`docs/plans/AUDIOWARE-DEPS-PLAN.md` ステップ2)のとおり、`resample.rs` が使う
比は**固定の有理数比 `L:M`**(44.1k↔48k なら 147:160 等)だけで、実行時に比を変える機能は
無い(§4.7 は再生速度変更を範囲外としている)。にもかかわらず旧実装は `rubato` の
`Fft`(FFT ベース、楽曲ストリーミング用)と `Async` sinc(補間テーブルによる近似、SE
一括変換用)という**用途ごとに異なるアルゴリズム**を使っており、`rustfft`/`realfft` 一族
6件を含む 13 クレートの表記義務を引き込んでいた。比が固定である以上、FFT も補間テーブルも
不要で、レート対ごとに1回だけ設計する固定のポリフェーズ係数を両用途で共有できる。

ADR-0003 により、この置き換えの前に Miri と fuzz の受け皿を用意し、fuzz が非有限入力
(NaN/inf)とレート0・極端な比での巨大確保を発見して `51b5853` で入口ガードを入れた。
自前実装でも同じ契約を保つ必要がある。

## 決定

### アルゴリズム

補間 `L` 倍 → 低域フィルタ → 間引き `M` 倍の標準的なポリフェーズ構成(Crochiere &
Rabiner)。ゼロ詰めは実際には行わず、出力サンプル `n_out` ごとに
`base = floor(n_out*M/L)`(参照する入力サンプルの位置)・`phase = (n_out*M) mod L`
(使うポリフェーズ部分フィルタ)を求め、`x[base], x[base-1], ..., x[base-(K-1)]` へ
その位相の係数(タップ数 `K`)を畳み込む。**一括変換([`resample_oneshot`])とストリーミング
([`StreamResampler`])は同じ畳み込みエンジン(`PolyphaseEngine`)を係数だけ変えて共有する**
(要件どおり1実装で両方を賄う)。

比が固定であることを使い、各位相の係数を**厳密に**事前計算する。rubato の非同期 sinc は
連続的な比に対応するため補間テーブル(オーバーサンプリング係数256)から位相を近似するが、
自前実装は位相がちょうど `L` 通りしかないことが分かっているため、この近似誤差が原理的に
無い。

### 窓関数: Kaiser

Kaiser 窓を選んだ(Blackman-Harris は不採用)。理由:

- 目標ストップバンド減衰量(dB)からベータを一意に決める式が確立している
  (`kaiser_beta`。Oppenheim & Schafer 等の標準的な経験式)。
- 与えたタップ数に対する遷移帯域幅も Kaiser の近似式(`(A-8) / (2.285 * 2π * N)`、`N` は
  ポリフェーズ展開前の全体タップ数 `K*L`)で見積もれるため、**カットオフをどこに置くべきか
  を逆算できる**(固定の「ロールオフ係数」を当てずっぽうで決めなくてよい)。
- `libsamplerate` 等、多くのポリフェーズ SRC 実装が採用する標準的な選択。

旧実装(`ONESHOT_WINDOW = BlackmanHarris2`)から変わるが、比較データ(下記)のとおり
振幅・周波数の精度は旧実装と同等以上であり、退行ではない。

### タップ数(1位相あたり `K`)と減衰目標

| 用途 | `K` | 目標減衰 | 理由 |
|---|---|---|---|
| ストリーミング(`StreamResampler`)| 64 | 80dB | デコードスレッドで `pump()` のたびに評価される。CPU コストと群遅延(`(K-1)/2` 入力サンプル)を抑える。64 タップは一般的な「中品質」sinc リサンプラ(例: libsamplerate の Medium Quality 相当)と同程度で、ゲーム音声としては十分 |
| 一括変換(`resample_oneshot`)| 256 | 100dB | ロード時の一度きりのコストなので、計算量よりストップバンド減衰(エイリアシング抑制)を優先する。旧実装の `sinc_len = 256` を踏襲 |

### カットオフの決め方

小さい方のレートのナイキスト周波数を目標にし、Kaiser の遷移帯域幅近似式から逆算した
ガードバンドぶんだけ手前(`design_polyphase` 参照)に置く。下限(ナイキストの5%、
[`MIN_CUTOFF_FRACTION_OF_NYQUIST`])は病的な組み合わせに対する安全弁で、実際にサポートする
レート対では触れない。

### レート比の安全域を2段にする

旧実装の `MAX_RATE_RATIO`(大きい方/小さい方 ≤ 256)に加え、**約分後の `L`/`M` の大きい方**が
`MAX_POLYPHASE_FACTOR`(8192)を超える組み合わせも拒否する。ポリフェーズ係数表のサイズは
`K*L` に比例するため、比自体が 1.0 に近くても互いに素に近い(`gcd` が小さい)レート同士
(例: 44100Hz と 44101Hz)だと `L`/`M` が独立に数万へ発散しうる——rubato `Fft` が
「`gcd` が小さいと FFT が巨大化する」弱点を持っていたのと同種の懸念で、旧実装のモジュール
doc にあった注記を自前実装でも同じ形で引き継いだ。実測(Python シミュレーション): 実在する
一般的なレート(8kHz〜192kHz)の組み合わせでは `L`/`M` の最大値は 2560(11025Hz↔64000Hz)。
8倍の余裕を見て 8192 を上限にした。

### 遅延(レイテンシ)

自前実装の群遅延(`(K-1)/2` 入力サンプル、出力レート換算は `convert_frame_count` と同じ
四捨五入)は rubato の `output_delay()` と**値が変わる**。ただし影響範囲は
`resample.rs` の中に閉じている:

- grep 済み(`output_delay|delay_to_skip|遅延`)。`convert_frame_count`・楽曲クロック
  (`clock.rs`)・FFI(`mw_get_output_latency_ns` は出力デバイスのレイテンシで無関係)の
  いずれもリサンプラの群遅延を織り込んでいる箇所は無かった。旧実装のモジュール doc が
  明言しているとおり、「生成直後・`reset()` 直後の出力から `output_delay()` フレームぶんを
  内部で読み捨ててから呼び出し側へ渡す」設計だったため、**遅延は最初から呼び出し側に
  一切見えていなかった**。
- したがって、自前実装でも同じ「内部で読み捨てる」契約を維持するだけで、`convert_frame_count`
  や楽曲クロック側の変更は一切不要だった(公開 API/FFI が遅延の値を返す約束も無い)。
- 回帰テスト(`resample.rs::tests::delay_is_a_deterministic_function_of_the_rate_pair`)は
  インパルスを通し、出力先頭付近(8フレーム以内)にピークが来ること——つまり群遅延の
  読み捨てが機能していること——を複数のレート対で固定する。

### 非有限入力・極端なレート比のガード(fuzz 由来、`51b5853` の契約を維持)

- `sanitize_sample`(NaN/inf → 0.0、`MAX_ABS_INPUT_SAMPLE` で clamp)を畳み込みの唯一の
  入力正規化ポイントとしてそのまま維持した。
- `validate_rates`(レート0・比が `MAX_RATE_RATIO` 超・約分後の `L`/`M` が
  `MAX_POLYPHASE_FACTOR` 超を拒否)を `StreamResampler::new`/`resample_oneshot` の両方が
  リサンプラ構築前に必ず通る、という構造も維持した。

## rubato との比較(置き換え前、ゴールデン確認)

比較には `crates/mw-core/src/resample.rs`(rubato 版、置き換え前の Git HEAD)と自前実装を
それぞれ切り出して1つの一時バイナリにリンクする、リポジトリ外(スクラッチディレクトリ)の
比較専用スクリプトを使った。**このスクリプトと以下の生データはリポジトリには残していない**
(before-after 比較テストを残さない方針。数値はこの ADR に記録する)。手法:

- `resample_oneshot` を rubato 版・自前実装の両方で同じ入力に対して実行。
- 正弦波(100/1000/5000/12000Hz)・インパルス・無音・短い入力(32フレーム)・
  L/R で異なる周波数(チャンネル独立性の確認)を、44.1k↔48k・32k→48k で変換。
- 相互相関で最良のラグを探してから `SNR = 10*log10(signal_power/error_power)`(dB)を計算。
- 遅延はインパルス応答のピーク位置(両実装とも群遅延を内部で読み捨てるため、
  ピークは出力先頭付近に来るはず)で比較。

結果:

| ケース | 44.1k→48k | 48k→44.1k | 32k→48k |
|---|---|---|---|
| 100Hz | 95.5dB | 99.6dB | 49.9dB |
| 1000Hz | 76.5dB | 79.7dB | 29.9dB |
| 5000Hz | 62.4dB | 65.6dB | 19.8dB(探索窓拡大で 30.8dB)|
| 12000Hz | 53.6dB | 56.6dB | 8.4dB |
| インパルスのピーク位置差 | 0 | 1 | 1(16k→48k も 1)|
| 無音 | both silent(SNR = -inf dB、誤差0)| — | — |
| 短い入力(32フレーム)| 38.3dB | 41.6dB | — |

44.1k↔48k(実運用で使う組み合わせ)は全帯域で 50dB 超と高い一致度。32k→48k は高域
(12kHz)で一致度が下がる(8.4dB)が、**これは自前実装の不具合ではない**——同じケースで
自前実装単体の周波数・振幅精度を独立に測ると、期待値(12000.0Hz、RMS 0.1414)と完全に
一致していた(rubato 側も同様に一致)。つまり両実装とも「正しい」が、位相応答の細部
(Kaiser 窓 vs BlackmanHarris2、厳密な位相 vs 補間テーブル近似)が異なるため、波形同士を
直接引き算すると差が大きく出る——SNR という指標の性質上、group delay 以外の周波数依存の
位相差(分散)が蓄積されると悪化しやすい。実際の合否判定は「置き換え後も残るテスト」
(`resample.rs::tests` の `oneshot_preserves_frequency_and_amplitude_*`・
`oneshot_attenuates_frequencies_above_the_output_nyquist_when_downsampling` 等、現在の
仕様の入力と期待出力だけを見るテスト)に一本化しており、この ADR の比較数値はあくまで
「置き換えて明らかに劣化していないか」の参考値。

## 影響・トレードオフ

- **依存**: `Cargo.toml` から `rubato` を削除(`rustfft`/`realfft`/`windowfunctions`/
  `audioadapter`/`audioadapter-buffers`/`audioadapter-sample`/`num-complex`/
  `num-integer`/`primal-check`/`strength_reduce`/`transpose` も連鎖して消えた)。
  `THIRD-PARTY-LICENSES.md` の「表記が要る」件数は **39 → 27(-12)**。`num-traits` だけは
  `cpal`(ステップ4で置き換え予定)が別途引き込むため残っている。
- **Miri**: `cfg_attr(miri, ignore)` だった `decode.rs` の6箇所・`wav.rs` の1箇所
  (rubato の FFT を Miri で解釈すると数分〜十数分かかるための退避)を全て外した。
  `resample.rs` 自体の unsafe は無い(純粋な安全な Rust の算術・ループ)ため、Miri の
  検査対象としての価値は主に「decode.rs/wav.rs の unsafe 経路をリサンプル込みで通す」こと。
- **遅延の値そのものは変わる**(旧: rubato の FFT/Async sinc 固有の遅延。新: `(K-1)/2`
  入力サンプル)。ただしどちらも呼び出し側には見えない設計だったため、`convert_frame_count`
  や楽曲クロックへの影響は無い。実機で確かめるべきことは「音質・遅延の値」そのものではなく
  「楽曲の頭出し・シーク後の再開に不自然な間や継ぎ目が無いか」(内部の遅延読み捨てが
  正しく機能していることの間接確認)。
- **32k→48k のような `L`/`M` が偏るレート対**は、44.1k↔48k ほど rubato と一致しないことを
  比較データで確認済み(上記)。実運用で楽曲・SE 双方が主に 44.1k/48k である前提
  (初期構築仕様『§4.7』「素材制作の推奨レートは 48kHz」)では影響は小さいと判断するが、
  32kHz 等の素材を多用するようになった場合は自前実装単体の周波数特性
  (`oneshot_attenuates_frequencies_above_the_output_nyquist_when_downsampling` 等)を
  見直すこと。
- **窓関数を Blackman-Harris から Kaiser に変更**——旧実装の一括変換(`ONESHOT_WINDOW`)が
  使っていた窓と異なるが、タップ数・減衰目標は同等以上にしてあり、比較データのとおり
  退行ではない。
