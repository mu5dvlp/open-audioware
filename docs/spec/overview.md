## 1. 概要

CRI Ware の大まかな代替となる、**音楽ゲーム向けオーディオミドルウェア**を Rust で自作する。
CRI の全機能の再現ではない。**音ゲーに必要な機能だけを絞って作る。**

### なぜ作るか 【確定】

テンプレート仕様「オーディオ抽象化」で明記したとおり、Unity 既定オーディオの弱点は2つ:

1. **タップ SE の再生開始遅延**(特に Android)。判定精度には影響しないが体感品質を落とす。
   CRI 採用の実質的な動機はここにある
2. **クロックの精度**。`AudioSettings.dspTime` は更新が離散的で、スムージングで補うしかない

このミドルウェアは上記2点を **OS のローレイテンシ音声 API を直接叩くことで根本解決**する。

### テンプレートとの関係 【確定】

- テンプレート側の受け口は `IAudioService` / `IMusicClock`(テンプレート仕様「オーディオ抽象化」)。
  ミドルウェアは **CRI と同格の「差し替え実装のひとつ」**であり、テンプレートの既定実装は
  あくまで `UnityAudioService` / `UnityMusicClock` のまま
- **本リポジトリはテンプレートのフェーズ進行とは独立に開発する。**
  依存関係は「テンプレート Phase 2 で `IAudioService` / `IMusicClock` の IF が確定してから
  アダプタ統合(M2 後半)に着手できる」の1点のみ。Rust 側(M0〜M2 前半)はいつでも始められる
- **アダプタの置き場所 【仮】**: テンプレート側の `App.Audio.Native` アセンブリ
  (テンプレートリポジトリに置く。`App.Audio.Cri` と同じ隔離方式 — CRI SDK が外部で
  アダプタがテンプレート側にあるのと同じ構図に揃える)。
  本リポジトリの UPM パッケージは**テンプレート非依存物のみ**
  (ネイティブバイナリ + 生成 C# バインディング + 薄い C# ラッパ `Mw.Native`)を含む。
  こうすることで、UPM 単体でも(テンプレート無しでも)コンパイル・検証できる

### 成功基準 【仮】

テンプレート仕様「デバッグ機能」の判定計測ハーネスと実測で検証する。

**基準端末【確定・2026-08-25】: iPhone 14 / iOS 26.6.1。**
テンプレート仕様の未決事項「プロファイル基準端末」もこれに揃える。
手元の2台(iPad 第8世代 / iPhone 14)のうち**ハードウェア出力レイテンシが不利な方**を選んだ
(iPad 5.0ms に対し iPhone 14 は 17.9ms)。緩い端末を基準にすると、厳しい端末で
目標を割っていることに気づけないため。

| 項目 | 目標 |
|---|---|
| SE トリガー → 出力 | **ミドルウェアの取り分 ≤ 10ms**(= コールバック待ち + I/O バッファ長)。かつ Unity 既定実装との A/B で有意に改善していること |
| クロック精度 | `SongTimeAt` 換算のジッタ **±1ms 以内**、単調増加。ドリフトは **フル尺曲で `|drift| ≤ 100ms`**(異常検出用の上限。理由は下記) |
| 安定性 | 通常プレイ1曲を通してアンダーラン 0 回 |
| 統合 | テンプレートのライブを VContainer の登録替えだけでネイティブ実装に切り替えて完走できる |

**ドリフトの条件を「なし」から上限値へ変えた理由【確定・2026-08-25】。**
実機計測(`docs/measurement-m1.md` §11)で -117ppm 程度のドリフトが出たが、
**この量は判定精度に影響しない**:

- ドリフトの正体は**音声ハードウェアの水晶とシステムタイマーの周波数差**で、
  100〜300ppm は普通に起こる
- 曲時間は「レンダリング済みフレーム数 ÷ サンプルレート」で作られるため、
  **譜面と音の関係はズレない**(どちらも「音の秒」で数えている)
- ズレるのは「タップ時刻(システム時計)→ 曲時間」の変換だけだが、
  **この相関は毎フレーム取り直している**ので累積しない

**判定精度を決めているのはジッタのほう**で、そちらは ±1ms のまま据え置く。
一方、桁違いのドリフトは**サンプルレートの取り違え**(44.1k を 48k と思い込む =
88000ppm)のような実装の異常を検出できるため、条件自体は上限値として残す。

**SE レイテンシの目標を「取り分」で定義し直した理由【確定・2026-08-25】。**
当初は「iOS ≤ 20ms」という end-to-end の絶対値だったが、実測の結果**この指標は
実装の良し悪しではなく端末の性質を測ってしまう**ことが分かった
(`docs/measurement-m1.md` §10.4)。同じミドルウェアが iPad 第8世代では 12.5ms で
目標を満たし、iPhone 14 では 25.4ms で満たさない。差は**ハードウェア出力レイテンシ
(5.0ms vs 17.9ms)**で、これは AVAudioSession が申告してくる値そのもの ——
**ミドルウェアが触れる層より下にあり、Unity 実装でも同じだけ払う**。

「取り分」= コールバック待ち + I/O バッファ長 で定義すると、両端末とも 7.5ms となり
端末をまたいで比較できる。end-to-end の絶対値が要るときは、この値に
`mw_get_output_latency_ns` の実測を足せば復元できる(情報は失われない)。

## 2. 決定事項サマリ

| # | 論点 | 決定 | 状態 |
|---|---|---|---|
| M1 | 実装言語 | **Rust**(stable)。コア・プラットフォーム層とも Rust で書き、OS 依存部のみ薄いシムを許容 | 【確定】 |
| M2 | 境界 | **C ABI(FFI)+ P/Invoke**。C# バインディングは **csbindgen** で自動生成 | 【仮】 |
| M3 | スレッドモデル | **リアルタイム音声スレッドはロック・アロケーション禁止**。ゲームスレッドとはロックフリーのコマンド/イベントキューで通信 | 【確定】 |
| M4 | コールバック | **C → C# のコールバックはしない**。イベントは C# 側が毎フレームポーリング(IL2CPP/Mono の逆呼び出しの複雑さを避ける) | 【確定】 |
| M5 | クロック | **音声スレッドのサンプルカウンタ + デバイスタイムスタンプの相関**を正とする(dspTime 方式より原理的に高精度) | 【確定】 |
| M6 | 出力バックエンド | 立ち上げは **cpal**(macOS Editor / iOS / Android を1系統で)。計測後、必要なら Android を **oboe 直叩き**、iOS を RemoteIO 直叩きに置換 | 【仮】 |
| M7 | デコード | **Symphonia**(wav / ogg vorbis)。楽曲は**メモリ上の圧縮データをストリーミングデコード**(ファイル IO を実行時に持ち込まない) | 【仮】 |
| M8 | 動作モード | **フルネイティブのみ**(BGM も SE もミドルウェア経由)。Unity 側 BGM + ネイティブ SE の混成モードは作らない — クロックの正が2つになるため | 【確定】 |
| M9 | 配布形態 | **UPM パッケージ**(git URL 参照)。**テンプレート非依存物のみ**を同梱(§1「テンプレートとの関係」)。`App.Audio.Native` アダプタはテンプレート側 | 【仮】 |
| M10 | 動画(Sofdec 相当) | **スコープ外**。`IVideoService` はテンプレート側で IF のみのまま | 【確定】 |
| M11 | リポジトリ | **`open-audioware`(本ディレクトリ)**。旧計画の未決事項(仮称 rhythm-audio)はこれで確定 | 【確定】 |
| M12 | 内部フォーマット | **f32 ステレオ固定でミックス**し、サンプルレートは出力デバイスに追従。素材は 48kHz を推奨し、不一致はリサンプルで吸収 | 【仮】 |
| M13 | 音量遷移の品質規約 | **すべての音量変化・停止はランプ(短いフェード)を通す**。ステップ変化によるクリックノイズを構造的に排除する | 【確定】 |
| M14 | 楽曲ボイス | **クロックを持つ楽曲ボイスは1本のみ**。M4 で BGM 用に<b>2本目</b>を足したが、<b>音楽クロックの発行元は1本目に固定</b>する(クロックの正を1つに保つ、という当初の理由はそのまま守られる)。BGM 側はクロックを持たず、ループ再生とフェードだけを扱う | 【確定】 |

## 3. スコープ

### 作るもの

- ローレイテンシの SE 再生(発音は次オーディオコールバック = 1バッファ以内)
- 楽曲のストリーミング再生: 予約再生(PlayScheduled 相当)/ ポーズ / 巻き戻し付き再開 / シーク / 停止
- サンプル精度の音楽クロックと、ホスト時刻(`Time.realtimeSinceStartup` 系)との相関 API
- バス(BGM / SE / Voice / Master): 音量、フェード
- サンプル精度のスケジュール発音(メトロノーム / キャリブレーション用クリック)
- 選曲プレビュー用のループ区間再生 + フェードイン/アウト
- 出力レイテンシの問い合わせ、出力ルート変化・アンダーラン・曲終了のイベント通知
- オフラインレンダリング(デバイス無しでバッファに書き出す)— テストと CI の土台
- 生成 C# バインディングと薄い C# ラッパ(`Mw.Native`)、UPM パッケージ
- 統合検証用の最小 Unity サンプルプロジェクト(テンプレート非依存)

### 作らないもの

- 動画再生(M10)
- DSP エフェクト(リバーブ等)、3D 空間音響 — 音ゲーコアに不要
- 録音、マイク入力(キャリブレーションの自動計測に将来使う可能性はあるが初期スコープ外)
- アセット暗号化(CRI にはあるが、テンプレート仕様「データ永続化」のチート対策水準に合わせて見送り)
- タイムストレッチ(ピッチ維持の速度変更)。譜面エディタの 0.5x 再生は
  当面リサンプリング(ピッチも下がる)で妥協し、必要になったら検討 【仮】
- ハプティクス — テンプレート側(Unity)の責務のまま
- `App.Audio.Cri` 的な他ミドルウェア対応 — テンプレート側の責務
