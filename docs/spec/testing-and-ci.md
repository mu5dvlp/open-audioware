## 8. テスト戦略 【確定】

- **オフラインレンダリングが主戦場**。mw-core をデバイス無しで駆動し、出力バッファを検証する:
  - ミキサ・音量・フェードの数値検証、ソフトクリッパの動作検証
  - **スケジュール精度**: 予約発音が指定サンプル位置ちょうどに乗っているかをサンプル単位で検証
    (バッファ内オフセット発音 §4.5 の検証を含む)
  - **クロック検証**: レンダリング済みフレーム数とスナップショットの整合、
    シーク・ポーズ・世代カウンタ跨ぎの単調性規約(§4.4)の検証
  - デコード正当性: 既知波形(テンプレートの生成音源と同系のシンセ波形)をエンコード → デコードし、
    位相・長さ・ゲインを許容誤差内で照合する**ゴールデンテスト**。ogg シーク精度もここで固定化。
    ゴールデン波形はテスト時にコードで生成し、バイナリはコミットしない(権利面・LFS 不要化)
  - リアルタイム安全性: デバッグアロケータフックによるコールバック内アロケーション検出(§5.3)
- **実機計測**: 成功基準(§1)の実測。SE 遅延は
  1. まず**外部録音**(別端末でタップ音と出力音を録り波形間隔を測る素朴な方法)で
     ミドルウェア単体を計測(M1。テンプレートに依存しない)
  2. テンプレート統合後は判定計測ハーネス(テンプレート仕様「デバッグ機能」)で計測(M2 以降)
- **Unity 統合テスト**: テンプレート側 PlayMode テストのオートプレイ通し
  (テンプレート仕様「品質管理」)をネイティブ実装差し替えで1本流す
- **契約的テスト**: `IMusicClock` / `IAudioService` の振る舞いテストを Unity 実装と共通化し、
  両実装に同じスイートを流す(テンプレート仕様の契約テストスイートと同じ思想。
  スイート自体はテンプレート側にあり、アダプタ実装がそれに合格する)

## 9. ビルド・配布・CI

### ビルドターゲット 【仮】

| ターゲット | 形態 | 用途 |
|---|---|---|
| aarch64-apple-darwin | .dylib | Unity Editor(開発の主環境) |
| aarch64-apple-ios | .a → xcframework | iOS 実機(静的リンク) |
| aarch64-linux-android | .so(cargo-ndk) | Android 実機 |
| x86_64 系 | 任意 | CI テスト実行用。Windows Editor 対応は当面見送り 【仮】 |

### 配布 【仮】

- UPM パッケージ(M9): `Plugins/` 配下にプラットフォーム別バイナリ、生成済み C# バインディング、
  `Mw.Native` ラッパ、最小サンプルを含める。パッケージ名 / 組織 ID は 【未定】(MU7)
- バージョニングは semver。**ABI 互換の破壊はメジャーバージョンでのみ許可**し、
  `mw_abi_version()` で実行時検証する
- リリースは GitHub Actions でタグ駆動ビルド(macOS ランナーで dylib / xcframework、
  Linux ランナーで Android .so)→ パッケージに固めて Release 添付

### CI 【仮】

- `cargo fmt --check` / `cargo clippy -D warnings` / `cargo deny check` / `cargo test`
  (mw-core はオフラインレンダリングでデバイス無しテスト可能)
- ターゲット4種のクロスビルドが通ることを常時検証(バイナリ配布はタグ時のみ)
