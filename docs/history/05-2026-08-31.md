## 作業① 再オープンを諦めたことを C# 側へ通知する

### 既存のイベント種別で表現できたか

**できた。新しい `Event`/`MwEventKind` バリアントは追加していない。**
`Event::AudioInterruptionEnded { recovered: bool }`(iOS の割り込み復帰通知として
M3 で先に存在していたもの)を転用した。

判断根拠:

- **意味が完全に一致する**: 「ストリームレベルの復帰を試みた結果」という抽象は
  iOS のセッション再アクティブ化も Android の内部再オープンも同じで、`recovered:
  bool` 1個で過不足なく表現できる。
- **発生源の排他性が cfg で保証されている**: iOS/tvOS では `ios_interruption.rs`
  の経路のみ、それ以外では `mw-ffi::reopen`(今回拡張した箇所)の経路のみが
  コンパイルされる(`04-2026-08-31.md`「iOS の既存経路を壊していないことを、
  何で担保したか」と同じ `cfg` 排他)。したがって単一のビルドの中では
  「どちらが発生源か」の曖昧さが生じない——C# 側が発生源を気にせず
  `recovered` だけを見て「音が戻ったか/戻っていないか」を判断できる。
- **「開始」通知(`AudioInterruptionBegan`)を新設する必要が無かった**: Android の
  切断そのものは既に `Event::StreamError { reason: DeviceUnavailable }` として
  通知済み(`cpal` の `err_fn` 経由、M3 より前から存在)。これが実質的に
  「開始」の役目を兼ねている。
- **新種別を足す場合のコスト**が見合わなかった: `MwEventKind` に値を足すと
  csbindgen 生成物(`NativeMethods.g.cs`)の再生成、C# `EventKind` への追加が
  必要になるが、それは今回の転用でも(後述の通り)結局必要になった。つまり
  「新種別を避けたことで C# 側の変更が完全にゼロになった」わけではないが、
  **mw-core/mw-ffi 側の enum 変更(`to_bits`/`from_bits`/`from_core` の新規
  match アーム追加、ABI 上の新しい判別子の確保)は避けられた**——これが
  「既存の種別で表現できるなら新種別を足さない」の実質的なメリット。

### 成功したときも通知することにしたか

**した。** `Instance::attempt_reopen` が成功した瞬間・バックオフを使い切って
「諦めた」瞬間の両方で `Event::AudioInterruptionEnded` を積む
(`Instance::notify_reopen_outcome`、`crates/mw-ffi/src/handle.rs`)。

判断根拠:

- 依頼書の示唆どおり、成功が分かればクライアントは「音が戻った」表示を消せる。
- 既存の iOS 側 `AudioInterruptionEnded` も元々 `recovered: true/false` の両方を
  常に積む設計(割り込み終了時は必ず1回積む、成功時だけ省略するような非対称
  設計にはなっていない)。Android 側だけ「失敗時のみ通知」にすると、同じ
  イベント種別なのに片方の発生源だけ非対称な運用になり、C# 側のハンドラが
  「このイベント、成功時は本当に来ないのか」を毎回確認しないといけなくなる。
  今回まさに直そうとしている R38 と同型の「無言で諦める」を、非対称な形で
  半分だけ再現してしまうことを避けた。
- **中間の失敗(バックオフ待機中)では積まない**——ここは非対称にしていない
  iOS 側とも一致(iOS 側もリトライ経過ごとに毎回イベントを積む設計ではない)。
  積むのは「これ以上自動では回復しない」ことが確定した瞬間
  (`ReopenPolicy::is_exhausted()` が新たに `true` になった瞬間)だけに絞った
  ——そうしないとバックオフ中の一時的な失敗のたびにイベントが積まれ、
  C# 側から見て「まだ試行中なのか、もう諦めたのか」が読み取りにくくなる。

### C# ラッパまで通したか

**通した。** `unity/Runtime/MwNative.cs` の `EventKind` に
`AudioInterruptionBegan = 6` / `AudioInterruptionEnded = 7` を追加した。

🔴 **副次的に見つけた既存の欠落**: この2値は Rust 側(`mw-ffi::event::MwEventKind`)
には M3(iOS の割り込み対応)の時点で既に存在していたが、**C# 側の `EventKind` は
`ClipperEngaged = 5` までしか無く、6・7 が丸ごと欠落していた**(`git log` 確認済み
——`MwNative.cs` は M4-3〔BGM〕まで更新されているが、この2値は一度も追加されて
いない)。今回 Android の再オープン結果通知に `AudioInterruptionEnded` を使う
ためにはこの欠落を埋める必要があり、結果として iOS 側の割り込み通知も今回
初めて C# から名前付きで読めるようになった(依頼書のスコープ外だが、今回の
作業を完了させるための必須の前提だったため実施した)。

あわせて `unity-sample/Assets/Tests/EditMode/MwNativeMusicEditModeTests.cs` に
`EventKind_ValuesMatchNativeDiscriminants`(判別子の数値がネイティブ側と
1:1で一致することを固定化するテスト)を追加した。**Unity を起動していないため
実行はしていない**(依頼書「ネイティブバイナリのビルドは不要」の趣旨に沿い、
Unity 起動も行っていない——`CLAUDE.md`「Unity 起動の直列化」の対象操作)。
C# のコンパイル可否・実行結果は次回 Unity を使うセッションで確認が要る。

Rust 側の統合テスト `run_reopen_lifecycle`(実ハンドル越し)を拡張し、再オープン
成功時に実際に `Event::AudioInterruptionEnded { recovered: true }` が
`mw_poll_events` 経由で観測できることをアサートするようにした
(`crates/mw-ffi/src/ffi.rs`)。**「諦めた」側(`recovered: false`)は自動テストで
確認していない**——`04-2026-08-31.md` から引き続き、この環境には
`CpalBackend::open` を確実に失敗させる手段(モックバックエンド)が無いため
(既存の制約そのまま)。配線自体(`if self.reopen.is_exhausted() { self.
notify_reopen_outcome(false); }`)は1行の条件分岐で、`ReopenPolicy` の
「使い切ったら `exhausted` になる」という遷移自体は `reopen::tests::
gives_up_after_exhausting_the_backoff_schedule_and_never_loops_forever` で
既に固定化済み。

### 実装中に踏んだ既存テストとの衝突(修正済み)

`run_event_poll_checks`(M2-6 由来、再オープンとは無関係な「FFI 境界の汎用ドレイン
挙動」を確認するテスト)が、テスト用の汎用イベントとして
`StreamError { reason: DeviceUnavailable }` を注入していた。この reason は
`Instance::note_stream_error` が内部再オープンの候補として拾う値そのものであり、
`mw_poll_events` の呼び出し末尾で `maybe_reopen` が実際に発火する
(この環境には実デバイスがあるため即座に成功する)。今回の変更前は成功しても
何も可観測な副作用が無かったため気づかれていなかったが、成功時にイベントを
積むようになったことで「フルドレイン後はキューが0件のはず」という
`run_event_poll_checks` 側の前提が崩れ、テストが落ちた
(`left: 1 right: 0`)。**再オープン機能そのものとは無関係なテストが、たまたま
選んだ reason 値のせいで無関係な機能と結合していた**のが真因。対策として、
このテストの注入 reason を `DeviceUnavailable` から `Backend` へ変更した
(意味的に「何らかのバックエンドエラー」を表す汎用値で、再オープンの対象外
——`Instance::note_stream_error` のドキュメント「`Reconfigured`/
`PermissionDenied`/`Backend` はここでは何もしない」参照)。再オープン専用の
検証は元から `run_reopen_lifecycle` に集約されているため、この変更で
カバレッジは失われていない。

## 作業② バックオフの値と「諦める条件」を見直せる形にする

**判断: いまのままでよい(`REOPEN_BACKOFF_SCHEDULE_MS` を `mw_core::config::Config`
へ設定項目として格上げしない)。**`crates/mw-ffi/src/reopen.rs` の `pub const`
のまま維持し、doc コメントに【仮】であることと判断根拠を明記した。

根拠:

1. **先例がある**: 同じ性質の値(`ios_interruption::RECOVERY_WAIT_SCHEDULE_MS`、
   OS 割り込み復帰の待機スケジュール)も `mw_core::config::Config` のフィールドでは
   なく、バックエンド固有の `pub const` として持たせている。`REOPEN_BACKOFF_
   SCHEDULE_MS` だけを `Config` へ格上げすると、この既存の「バックエンド/FFI固有の
   復旧タイミングは対象クレートにローカルな定数」という流儀と非対称になる。
2. **実際には誰も上書きできない**: `mw_init` は現時点で C# 側から設定値を注入する
   経路自体を持たない(`Config` 自身のドキュメント「M1 時点では FFI からの
   上書きは未実装。M8 相当」)。`Config` へ移しても、それを実際に書き換える
   手段(FFI 引数・環境変数等)がどこにも無いため、複雑さが増えるだけで
   実質的な柔軟性は得られない。
3. **初期構築仕様の凡例「【仮】」が要求する構造**(「1箇所を書き換えれば済む
   構造〔設定構造体 **/ 定数**〕」)は、この `pub const REOPEN_BACKOFF_SCHEDULE_MS`
   1個で既に満たしている——配列を直接書き換えるだけで済む1箇所。

対応として、`reopen.rs` の doc コメントに **【仮】** タグを明記し、実機の実測分布を
見ていないこと・見直す場合はこの配列1箇所を書き換えれば済むこと・`Config` へ
意図的に移していない理由を追記した(コード側のコメントを読むだけで「これは
仮の値である」ことが分かる状態にした、という依頼書の要求を満たす)。
`crates/mw-ffi/CLAUDE.md` にも同じ趣旨を1文添えた。

## 判断に迷い、勝手に確定させなかった点

1. **`Event::AudioInterruptionEnded` という名前を Android 用に転用したこと**。
   バリアント名は「Interruption」のままで、Android の実態(デバイス切断からの
   内部再オープン)を直接表す言葉ではない。リネーム(例:
   `AudioRecoveryEnded`)も検討したが、既存の iOS 側ドキュメント・テスト・
   3クレートにまたがる参照を巻き込む変更になる割に、動作は一切変わらない
   (waiting for a rename to be worth the diff)。doc コメントで両方の発生源を
   明記する形に留めた——名前の是非も含め、ユーザー判断を仰ぎたい。
2. **`StreamErrorReason` に C# 側の対応 enum が無いこと**(今回は未対応・
   スコープ外)。`unity/Runtime/MwNative.cs` は `EventKind.StreamError` の
   `payload`(理由コード)を解釈する enum を最初から持っておらず、今回の
   作業とは無関係な既存の欠落として見つかった。今回の通知経路
   (`AudioInterruptionEnded`)はこれに依存しないため直さずに残した——
   直すかどうかは別途判断してほしい。
