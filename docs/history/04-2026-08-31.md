## `Instance` の所有設計をどう変えたか(いちばん知りたい点への回答)

**当初懸念されていたほど大きな再設計にはならなかった。** `handle::init`/`handle::
shutdown` が既に「レジストリの `Mutex<Option<Instance>>` を直接ロックして `&mut
Instance`(または所有権そのもの)を得る」という経路を持っていたことに気づいたのが
分岐点——`mw_poll_events` 等の通常 FFI 呼び出しが使う `with_instance`(`&Instance`
のみを渡す)とは別に、**同じレジストリロックを使う `&mut Instance` 経路をもう1つ
増やすだけで済んだ**:

```rust
pub fn maybe_reopen(handle: u64) {
    let mut guard = registry().lock()...;
    let Some(instance) = guard.as_mut() else { return; };
    if instance.handle != handle { return; }
    let now_ns = mw_backend::host_time_ns();
    if !instance.reopen.is_due(now_ns) { return; }
    instance.attempt_reopen(now_ns);
}
```

これにより、`command_sender` / `reclaim_receiver` / `music_clock` / `bgm_state` /
デコードスレッド一式(`decoder_tx`/`decode_thread_stop`/`decode_thread` とその BGM
版)は**フィールドの型を一切変えていない**(`Mutex`/`ArcSwap` 等の追加の間接参照は
導入していない)。`attempt_reopen(&mut self, ...)` の中で単純代入
(`self.command_sender = command_sender;` 等)で差し替えるだけで足りる——
`maybe_reopen` がレジストリの排他ロックを握っている間、他のどの FFI 呼び出し
(`with_instance` 経由)も同じロックの取得待ちでブロックされるため、「差し替えの
途中を誰かが読んでしまう」競合状態が構造的に起こらない(`init`/`shutdown` が
最初から拠り所にしていたのと同じ排他性)。

**再オープンの起点は `mw_poll_events` そのもの。** 専用の監視スレッド・ポーリング
タイマは新設していない——C# 側が毎フレーム呼んでいる既存の関数を「ドレイン後、
切断を見ていればバックオフ条件を満たす場合だけ `maybe_reopen` を1回呼ぶ」よう
拡張しただけ(依頼書「⚠️ 再オープンはゲームスレッド側でやること」を、既存の
ゲームスレッド駆動点に相乗りする形で満たした)。

**新規追加**:

- `crates/mw-ffi/src/reopen.rs`(新規モジュール): `ReopenPolicy` ——
  「いつ再試行するか/いつ諦めるか」だけを判定する、OS/バックエンド呼び出しを
  一切含まない純粋な状態機械。`mw-backend::ios_interruption::InterruptionState`/
  `confirm_recovery_progress` と全く同じ設計方針(判定ロジックは純粋な値、
  副作用は呼び出し側)を踏襲した。バックオフスケジュール
  `REOPEN_BACKOFF_SCHEDULE_MS = [250, 500, 1_000, 2_000, 4_000]`(ms)。
  合計6回の試行(5つの待機区間)を使い切ると `exhausted` になり、以後
  `is_due` は新しい切断イベント(`mark_pending`)が来るまで恒久的に `false`
  を返す——詳細は「再オープン失敗時の振る舞い」節。
- `Instance` に復元用キャッシュを追加(`Renderer`/`Mixer` の外側に置く必要が
  あるため——再オープンでまるごと作り直される側に置くと復元の材料そのものが
  消えてしまう): `last_music_sound_id` / `last_music_loop` / `last_bgm_sound_id`
  / `last_bgm_loop` / `bus_volumes: [AtomicU32; 4]`(f32 を `to_bits` で格納)。
  `mw_music_set`/`mw_music_set_loop`/`mw_bgm_set`/`mw_bgm_set_loop`/
  `mw_bus_set_volume`/`mw_bus_fade` が成功するたびに更新する(`Instance::note_*`
  系メソッド)。
- `Instance::attempt_reopen(&mut self, now_ns) -> bool`: 本体。手順は
  (1) 壊す前に `music_clock.snapshot()`/`bgm_state.read()`/上記キャッシュを読む
  → (2) `backend.close()` + デコードスレッド停止・join(`stop_and_join_decode_
  threads`、`shutdown()` と共通化した) → (3) `Renderer::build_with_events(...)`
  で新しい `Mixer`/コマンドキュー一式を作る(**`events` の `Arc` identity は
  変えない**、後述) → (4) `MusicClockPublisher::seed_generation_after_reopen`
  で世代を仕切り直す → (5) `backend.open(...)` → 成功したらフィールドを差し替えて
  デコードスレッドを再スポーンし、状態復元コマンドを再送する。

## mw-core 側の変更(小さい2つ)

- `mw_core::clock::MusicClockPublisher::seed_generation_after_reopen(&self,
  generation: u32)`: 新しく作った(=`generation=0`から始まる)クロックを、
  誰にも公開する前に「直前のクロックが最後に観測させた値+1」でシードする
  ための専用 API。既存の `bump_generation`(内部で `wrapping_add(1)` するだけ)
  では「たまたま同じ値に戻ってしまう」ケースを塞げない(例: 一度もシークして
  いない曲は世代0のまま——新しいクロックも0から始まるので、シードしないと
  C# 側が不連続を見逃す)。`seed_generation_after_reopen(old_generation.
  wrapping_add(1))` を呼ぶことで「直前に観測されたどの値とも異なる」ことを
  保証する。単体テスト2本(`seed_generation_after_reopen_sets_generation_
  without_disturbing_other_fields` / `..._wraps_without_panicking`)。
- `mw_core::mixer::build_with_events` / `mw_core::renderer::Renderer::
  build_with_events`: 既存の `build`/`Renderer::build` はそのまま(新しい
  `EventQueue` を作る)残し、**呼び出し側が渡した `Arc<EventQueue>` をそのまま
  使う**別の入口を追加した。これにより再オープンをまたいで `mw_poll_events`
  が読み出す `EventQueue` の identity が変わらず、`Instance.events` フィールド
  自体を差し替える必要が無くなる(＝ここでも追加の間接参照が不要になった)。
  単体テスト1本(`build_with_events_reuses_the_given_event_queue_identity`、
  `Arc::ptr_eq` で identity を確認)。

## 復元できた状態・できなかった状態

**復元できた(実ハンドル越しの統合テストで実測済み)**:

- **楽曲の再生位置**(いちばん重要): `MusicClockSnapshot::song_frames` を
  `MusicPrepare` → `MusicSeek{frames: song_frames}` → (再生中だった場合のみ)
  `MusicPlayScheduled{host_time_ns: now}` として再送する。**新しいコマンド列を
  発明していない**——`mw_music_set` が既に使っている「デコーダ差し替え→
  Prepare→Seek」の順序厳守パターンをそのまま踏襲し、`MusicPlayScheduled` の
  「プリロール未完了なら Ready になるまで自動的に繰り下げる」既存の仕組み
  (`mixer::MusicSchedule`, 初期構築仕様『§4.3』)にそのまま乗せることで、
  ゲームスレッド側で「Ready になるまで待ってから再生コマンドを送る」独自の
  待ち合わせを一切書かずに済んでいる。
- **バス音量**: 4本とも `SetBusVolume` を再送する(`bus_volumes` キャッシュから)。
- **ロード済みの `SoundId`**: **追加の復元処理が一切不要だった**——`Instance::
  sounds`(SE)/`Instance::music_bytes`(楽曲圧縮バイト列)はどちらも
  `Renderer`/`Mixer` の外側、`Instance` 直下に元からあるストレージで、
  `attempt_reopen` はここに一切触れない。設計上「壊れようがない」。
- **ループ設定**: `last_music_loop`/`last_bgm_loop` キャッシュから
  `MusicSetLoop`/`BgmSetLoop` を再送する。
- **generation の bump**: 🔴 必須要件。上記の「シード」により、再オープンの
  たびに必ず「直前に観測されたどの値とも異なる」新しい世代へ切り替わる。

**復元しなかった(意図的な割り切り。判断根拠は下記)**:

- **効果音(SE)の発音**: 依頼書で明示的に「捨ててよい」とされていた通り、
  何もしていない。`VoicePool` は `Renderer::build_with_events` によって
  丸ごと新規生成されるため、鳴っていた SE ボイスは失われる。
- **BGM の再生位置・自動再開**: `mw_core::BgmStatePublisher` は
  `MusicState`(4値の状態)だけを公開する設計で、**そもそもフレーム位置を
  読み出す経路が無い**(M14「BGM はクロックを持たない」——位置を公開する
  仕組み自体が存在しない)。ロード済みトラック・ループ区間は復元するが、
  再生中だった場合も自動では再生を再開しない(`Ready` で止める)。
  理由: BGM の再生開始(`Command::BgmPlay`)は `MusicVoice::play()` が
  `Ready` 状態でのみ有効という**即時 API**で、楽曲側の `MusicPlayScheduled`
  (プリロール未完了なら自動的に繰り下げる仕組み)に相当する「準備完了を
  待ってから発火する」経路が BGM には無い。ゲームスレッドをブロックして
  `Ready` になるまでスピン待機する実装も検討したが、再オープンという
  1回きりの処理のために新しい待ち合わせパターンを mw-core 側に持ち込む
  ほどの価値は無いと判断し見送った——BGM はメタ画面のループ BGM 用途
  (初期構築仕様『§2』M14)であり、無音に戻ってもゲーム進行(判定)には
  影響しない。クライアント側が `mw_bgm_state` をポーリングして `Ready` を
  検知したら `mw_bgm_play` を呼び直せば復帰できる(この経路自体は既存の
  `mw_bgm_*` API だけで完結する)。
- **`Paused` 状態そのもの**: 楽曲が `Paused` だった場合、位置は復元するが
  明示的な再生はせず `Ready` で止める(ネイティブ側だけで `Paused` を
  再現する経路は用意していない)。`mw_music_resume_at`/`mw_music_pause`
  を呼べる状態まで戻すところまでが復元の範囲、という割り切り。
- 🔴 **既知の穴(実装中に発見)**: 再オープンの直前に `mw_sound_release` で
  楽曲/BGM の ID を解放していた場合(「再生中でも拒否せず解放を受け付ける」
  既存仕様、`Instance::remove_music_bytes` 参照)、`attempt_reopen` は
  `get_music_bytes` が `None` を返すため復元を諦める(ログを残して
  当該ボイスの復元だけスキップ、他の復元は継続する)。統合テストで実際に
  この分岐(BGM 側)を踏んだ——`run_bgm_lifecycle` が末尾で `bgm_id` を
  release していたため、後続の `run_reopen_lifecycle` の再オープンで
  「cannot restore bgm, sound_id ... is no longer loaded」のログが実際に
  出た。存在しない音を捏造しないという設計判断の結果であり、バグではない
  が、依頼書に明記の無い割り切りなので報告する。

## 再オープンに失敗したときの振る舞いと判断根拠

**バックオフ付きで最大6回試行し、それでも失敗したら諦める(無限リトライしない)。**
`ReopenPolicy`(`crates/mw-ffi/src/reopen.rs`)が判定を持つ:

- 待機スケジュール `[250, 500, 1_000, 2_000, 4_000]` ms。合計7.75秒。
  `ios_interruption.rs::RECOVERY_WAIT_SCHEDULE_MS`(合計370ms)より大幅に
  長くした理由: あちらは「OS が既に切り替え終えたルートへの `pause()`→
  `play()` 再試行」で数十〜数百msのタイミング差の問題だが、こちらは
  「デバイスの列挙・ストリーム構築が現実に間に合うようになるまで」を
  待つ必要があり、依頼書が指摘する「`default_output_device()` が切断直後に
  使える保証は無い」を汲んで長めに取った。
- 使い切ったら `exhausted = true` になり、`is_due` は以後ずっと `false`
  ——`mw_poll_events` を毎フレーム呼び続けても `CpalBackend::open`(相応の
  コストを伴う処理)を無駄撃ちしない。
- **ただし恒久的に詰むわけではない**: 新しい `DeviceUnavailable` イベントが
  届けば(実機なら、別の要因でもう一度切断が起きた場合等)`mark_pending` が
  新規サイクルとして自動的に仕切り直す。実装中に見つけたバグ(下記)を
  塞いだことで、この「新規サイクルへの復帰」が実際に機能することを
  単体テストで固定化してある。
- 🔴 **実装中に見つけて直したロジックバグ**: 当初の `mark_pending` は
  「既に `pending` なら何もしない」だけの判定だった。これだと、
  `exhausted` になった後は `pending` が `true` のまま二度と `false` に
  戻らない(`record_result(true, _)` = 成功時にしかクリアされない)ため、
  **諦めた後に届く新しい切断イベントが未来永劫無視される**——依頼書の
  意図(「バックオフか、諦めてイベントで通知するか」)に反して「一度
  失敗したら永久に直らない」になってしまう欠陥だった。統合テスト
  `reopen::tests::a_fresh_disconnect_after_giving_up_starts_a_new_cycle`
  がこれを実際に検出し(赤→原因特定→`mark_pending` を「`pending` で
  なかった、**または既に諦めていた**」場合にリセットする形へ修正→緑)、
  今は回帰として固定化されている。
- **失敗そのものをイベントで通知するかどうか**: 依頼書は「バックオフか、
  諦めてイベントで通知するか」を選択肢として提示していたが、**新しい
  イベント種別は追加していない**(判断)。理由: 最初の切断そのものは
  既に `Event::StreamError { reason: DeviceUnavailable }` として届いて
  おり、C# 側はこの1件だけで「切断が起きた」ことを既に知りうる。再試行の
  成否ごとに新しいイベント種別を増やすと `MwEventKind`(csbindgen 生成
  物)の変更が要り、影響範囲がクライアント側の C# バインディング再生成
  にまで広がる。今回は `mw_log!` での実機診断ログ(試行回数・諦めた
  ことを明記)に留め、イベント種別の追加は見送った——**この判断は
  勝手に確定させた**ので、「クライアント側が『再オープンを諦めた』こと
  を能動的に知る手段が要るか」はユーザー判断を仰ぎたい(下記「判断に
  迷った点」参照)。

## 🔴 iOS の既存経路を壊していないことを、何で担保したか

**3段構え**:

1. **`ios_interruption.rs` を1バイトも変更していない**(このセッションの
   diff に含まれない)。
2. **新しい再オープン機構の呼び出し口を `#[cfg(not(any(target_os = "ios",
   target_os = "tvos")))]` で丸ごとコンパイルから除去した**(`ffi.rs::
   mw_poll_events` 内、`handle_registry::maybe_reopen(handle)` を呼ぶ
   唯一の箇所)。「どちらの経路を通るか」は実行時の分岐・ヒューリスティック
   では一切なく、**コンパイル時の `cfg` 1箇所だけ**で確定する
   (依頼書「⚠️『どちらの経路を通るか』の判定を曖昧にしないこと」への
   直接の回答)。
3. **上記2の主張をツールで実測して裏取りした**(推測で終わらせなかった)。
   `cargo check -p mw-ffi --target aarch64-apple-ios` を実行すると、
   `attempt_reopen`/`restore_bus_volumes`/`restore_music`/`restore_bgm`/
   `maybe_reopen`/`ReopenPolicy::is_due`/`is_exhausted`/`attempts`/
   `record_result` が **すべて `dead_code` 警告として検出される**
   ——Rust コンパイラの到達可能性解析そのものが「iOS ターゲットでは
   これらの関数へ到達する呼び出し経路がゼロである」ことを裏付けている。
   同じ `cargo check -p mw-ffi --target aarch64-linux-android`(および
   ホストの macOS ビルド)では同じ関数群が warning ゼロ(＝実際に使われて
   いる)。iOS ビルドと Android/macOS ビルドを両方測ることで、`cfg` が
   意図どおり「両方向」に効いていることを確認した(iOS で消えているのが
   偶然の dead code ではなく、cfg の効果であることの確認)。
   ⚠️ **これは静的な到達可能性の確認であり、実機での動作確認ではない**
   ——`ios_interruption.rs` 自身の実機挙動(R12/R13/R24/R30 で直したもの)
   は今回のセッションで一切触っていないので変化していないはずだが、
   「触っていないことの確認」自体はビルドログでしかできない(実機での
   再検証はしていない、後述「実機でしか確認できない範囲」参照)。

  返すか**——`REOPEN_BACKOFF_SCHEDULE_MS` の妥当性(7.75秒で足りるか)は
  実機の実測でしか判断できない。
- **`backend.open()` が実機で実際に失敗するケースがあるか、あるとしたら
  どんなエラーか**——このセッションのテストはすべて「同じ実デバイスが
  引き続き存在する」状況(切断イベントは注入だが、デバイス自体は消えて
  いない)でしか再オープンの成否を確認できていない。真の切断(デバイス
  列挙から消える)状況での `backend.open()` の挙動は未検証。
- **`MusicPlayScheduled` による自動再開が、実機の AAudio 再オープン後にも
  同じタイミングで機能するか**——このセッションの検証は macOS(CoreAudio、
  常に同じデバイスが存在する環境)でのみ行った。
- **再オープンによる無音区間の長さ**(体感品質)。このセッションでは
  「音が戻ること」の論理的な正しさは確認したが、実際に何秒無音になるかは
  測っていない。

1. **再オープン失敗を諦めた際、専用イベントで C# 側へ通知するか**

   `mw_log!` のみに留め、`MwEventKind` の追加は見送った。

   スピン待機を足せば自動再開できるが、価値に見合わないと判断して見送った

   まで繰り下げる」仕組み)を追加すれば解決できる設計にはなっている
   (現状は意図的に持たせていないだけ)。
3. **`REOPEN_BACKOFF_SCHEDULE_MS` の値(合計7.75秒・6回試行)**——実機の
   実測が無いまま決めた【仮】値。長すぎる/短すぎるかは実機でしか判断
   できない。
