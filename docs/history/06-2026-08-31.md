## 作業① 現状のズレの洗い出し

`crates/mw-ffi/src/{result,types,event,ffi}.rs`(`extern "C"` 境界の全定義)と
`unity/Runtime/MwNative.cs`(手書きラッパ)を突き合わせた。前提として、
`unity/Runtime/Generated/NativeMethods.g.cs` は csbindgen が `build.rs` で毎回
上書き生成する完全自動生成物(`.gitignore` 対象・未コミット)なので、**そちら自体は
構造的にズレようがない**——ズレが起きうるのは「生成コードの `internal` 型を隠す
ために手で書き写した公開ラッパ」だけ、という前提でスコープを絞った。

### 見つけて埋めたもの

1. **`StreamErrorReason` に対応する C# enum が無かった**(持ち越し課題そのもの)。
   `mw_core::StreamErrorReason`(`#[repr(u32)]`, `Unknown=0`/`DeviceUnavailable=1`/
   `Reconfigured=2`/`PermissionDenied=3`/`Backend=4`)は `EventKind.StreamError` の
   `payload` の実体だが、C# 側に対応する型が最初から存在せず、呼び出し側は
   生の `ulong` を自分でキャストするしかなかった。`unity/Runtime/MwNative.cs` に
   `public enum StreamErrorReason`(同名・同値)を追加し、`EventKind.StreamError`
   の doc コメントからも参照するようにした。
   - **なぜ csbindgen に任せられないか**: この型の定義は `mw-ffi` ではなく
     `mw_core` にあり、`extern "C"` 関数のシグネチャにもどの構造体のフィールド
     型にも直接現れない(常に変換済みの `u64` としてしか FFI 境界を越えない)。
     csbindgen は「シグネチャに直接現れる型とその依存型」しか辿らないため、
     この型を自動生成する経路が原理的に存在しない(`crates/mw-ffi/CLAUDE.md`
     「`bus`/`mode` を `i32` で受け取る理由」と同じ制約の派生形)。**恒久的に
     手動同期が必要**——だからこそ作業②の自動検出テストの対象に含めた。
2. **`mw_get_output_underrun_stats`(M3 で追加)を呼ぶ C# ラッパが丸ごと存在
   しなかった**。ネイティブ側の関数自体(`crates/mw-ffi/src/ffi.rs`)・対応する
   blittable 構造体 `MwOutputUnderrunStats`(csbindgen 生成済み、`Generated.cs`
   に実在)はどちらも M3 の時点で揃っていたが、`unity/Runtime/MwNative.cs` から
   一度も呼ばれておらず、公開 API 一覧(`crates/mw-ffi/CLAUDE.md`)には載って
   いたのに実際には C# から到達不能だった。`MwNative.GetOutputUnderrunStats`
   と、非 blittable の詰め替え用公開構造体 `OutputUnderrunStats`(`MusicPosition`
   と同じ設計方針)を追加した。
3. **`EventKind.RouteChanged` の doc コメントが古いままだった**(ABI 値そのものは
   ズレていない、ドキュメントのみの陳腐化)。「検知そのものは M3 の範囲で、現時点
   では発火しない」という記述が残っていたが、実際には M3 で iOS/tvOS 側の実装
   (`crates/mw-backend/src/ios_interruption.rs`)が完了しており、ルート変化の
   たびに実際に発火する。コメントを現状に合わせて修正した。

### 判断が要ると考え、埋めずに報告する点

今回の洗い出しでは、値・シグネチャ・構造体レイアウトのレベルで「意味を変える/
命名を変える必要がある」ズレは見つからなかった。念のため確認した範囲と結果:

- `MwResult`(14種)・`MwBus`(4種)・`MwSoundMode`(2種)・`MwMusicState`(4種)・
  `MwEventKind`(8種、`AudioInterruptionBegan`/`Ended` を含む)は全て Rust 側と
  C# 側で名前・判別子が一致(このあと作業②のテストで機械的にも確認)。
- `extern "C"` 関数28個(`mw_abi_version`〜`mw_poll_events`)のシグネチャは、
  `mw_get_output_underrun_stats` を除き全て C# 側の呼び出しと引数の型・個数・
  順序が一致していた。
- blittable 構造体(`MwEvent`=16byte, `MwMusicPosition`=32byte,
  `MwOutputUnderrunStats`=24byte)はいずれも Rust 側で `size_of` の回帰テスト
  済み。`MwEvent` を直接ポインタ再解釈キャストする C# 側の `MwEventData` の
  フィールド順序(`Kind`, `Payload`)も一致(作業②で自動検証対象に追加)。
- ABI バージョン定数(`mw_abi_version() == 1`)と C# 側
  `MwNative.ExpectedAbiVersion == 1` も一致(作業②で自動検証対象に追加)。

## 作業② ズレを自動検出する仕組み

### 検討した候補と選んだもの

依頼書に挙がっていた3案のうち、**「Rust 側のテストで C# ソースを読んで判別子を
突き合わせる」を採用した**(`crates/mw-ffi/src/csharp_abi_sync.rs`、
`#[cfg(test)]` 専用モジュール)。

- ❌ **cbindgen 等でヘッダ生成 → 差分検出**: このリポジトリは既に csbindgen を
  採用済みで、生成物とズレるべき「手書きヘッダ」がそもそも存在しない
  (生成物は毎回上書きされ、手書きの薄いラッパ `MwNative.cs` だけが独立して
  存在する構造)。ズレの発生源が「生成コード vs 手書きヘッダ」ではなく
  「Rust 側の真実 vs 手書きラッパの公開列挙」なので、この案はこのリポジトリの
  実際のズレの発生パターンに対応しない。
- ❌ **Rust 側が判別子一覧を出力し、C# 側テストが突き合わせる**: 依頼書の注記
  「Unity を起動しないと検出できない形は不可」に抵触する——C# 側で何かを
  `assert` するテストを書く時点で、それを実行する手段は結局
  Unity Test Runner(EditMode)しかなく、このプロジェクトは Unity テストを
  CI で回さない方針(`../../CLAUDE.md`)。
- ✅ **Rust 側のテストが C# ソース(`unity/Runtime/MwNative.cs`)を読んで
  突き合わせる**: `cargo test --workspace` だけで完結し、Unity にもネットワーク
  にも依存しない。`include_str!` でコンパイル時にソースへ埋め込むため、実行時の
  ファイル探索も相対パスの解決も不要。

### 実装の要点(二重の防御)

1. **コンパイル時**: `MwResult`/`MwSoundMode`/`MwBus`/`MwMusicState`/
   `MwEventKind`/`mw_core::StreamErrorReason` それぞれについて、ワイルドカード
   無しの `match`(`describe_mw_event_kind` 等)で全判別子を名前へ変換する関数を
   置いた。Rust 側に新しい判別子(variant)を追加すると、この `match` が
   非網羅になり **`mw-ffi` クレート自体がコンパイルできなくなる**。つまり
   「新しい判別子を Rust に足したのに、誰もこのテストファイルへ触れないまま
   コミットされる」という事態がそもそも起こり得ない——追加した本人が必ず
   ここへ来て、対応する C# 側の値も一緒に更新する動線になる。
2. **実行時**(`cargo test`): 1で得た「(名前, 判別子)の全件」を、
   `unity/Runtime/MwNative.cs` から正規表現ではなく素朴なテキスト走査
   (XML doc コメント行を除外してから `Name = Value,` 形式を拾う)で抽出した
   C# 側の値と突き合わせる。名前の集合の過不足・値のズレの両方を1回の
   `assert!` でまとめて報告する。C# 側に対応する `enum` ブロックが**見つからない
   場合は panic**(fail-closed。黙ってスキップしない)。
   あわせて `mw_abi_version()` と C# `MwNative.ExpectedAbiVersion` の一致も
   同じモジュールで確認する。

### 実際に C# 側を壊してテストが落ちることを確認した(3パターン)

依頼書の要求どおり、テストが本当に効くことを実際に壊して裏取りした
(`unity/Runtime/MwNative.cs` を一時的に改変 → `cargo test` 実行 → 失敗を確認 →
元に戻す。`diff` で完全復元を確認済み)。

1. **背景のバグそのものを再現**: `EventKind` から `AudioInterruptionEnded = 7,`
   を削除 → `mw_event_kind_matches_csharp_event_kind` が
   `C# `EventKind` に `AudioInterruptionEnded` が無い(Rust
   `MwEventKind::AudioInterruptionEnded` = 7)` というメッセージで失敗することを確認。
2. **値のズレ**: `Bus.Voice = 3` を `9` に変更 → `mw_bus_matches_csharp_bus` が
   `` `Voice` の値がズレている: Rust `MwBus::Voice` = 3, C# `Bus.Voice` = 9 ``
   というメッセージで失敗することを確認。
3. **今回埋めた2件目の欠落を再現**: `StreamErrorReason` の enum ブロックを
   丸ごと削除 → `stream_error_reason_matches_csharp_stream_error_reason` が
   「`enum StreamErrorReason` が見つからない」という明示的なメッセージで
   失敗することを確認。

いずれも復元後は `cargo test --workspace` が全件通ることを確認済み。
