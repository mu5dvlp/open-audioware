## P3-8 —— C# ラッパが CI で一度もコンパイルされていなかった

残り4件で**唯一のメモリ破壊クラス**だった項目。

`unity/Runtime/Generated/NativeMethods.g.cs` は csbindgen が毎回生成し直すので構造的にズレない。
問題は**手書きの `unity/Runtime/MwNative.cs`** ——生成された blittable 構造体のフィールドを
`native.song_frames` のように名指しで詰め替えている。Rust 側が変わると
**壊れるのは C# のコンパイルだけ**で、`cargo test` は全部緑のまま通る。
そして **Unity のテストは CI で回さない方針**(コーヒー基準)なので、
**この C# は CI で一度もコンパイルされていなかった。**
気付くのはテンプレート利用者が IL2CPP ビルドを回したとき、という状態だった。

### 🔴 ズレ方が2種類あり、検査も2つ要る

**これが今回いちばん大事な発見。** 実測で確認した:

| ズレ方 | `dotnet build` | `offset_of!` assert | サイズ assert |
|---|---|---|---|
| フィールド名が変わった / 型が変わった | 🔴 **落ちる** | 通る | 通る |
| フィールドの**順番が入れ替わった** | ✅ **エラー0 で通ってしまう** | 🔴 **落ちる** | 通る(32 のまま) |

⚠️ **並べ替えは名前も型も enum の値も全部合ったまま**なので、既存の
`csharp_abi_sync.rs` の enum 突き合わせも `dotnet build` も素通りする。
そして C# 側は **黙って隣のバイトを読む** —— 結果はクラッシュではなく
「それらしい値」なので、音がずれる・時計が飛ぶという形でしか表に出ない
(`MwMusicPosition` は初期構築仕様『§4.4』の音楽クロックそのもの)。

実測の手順: `MwMusicPosition` の `is_playing`(`u8`)と `generation`(`u32`)を入れ替えたところ、
`dotnet build` は**エラー0**、`size_of` も **32 のまま**、`offset_of!` assert だけが落ちた。

### 入れたもの

1. **`tools/csharp-abi-check/MwAbiCheck.csproj`** —— Unity 非依存の最小プロジェクト。
   `MwNative.cs` は `UnityEngine` に一切依存していない(`using` は
   `System.Runtime.InteropServices` と生成名前空間の2つだけ)ので Unity 無しで通る。
   🔴 **この性質は意図して維持すること** —— `UnityEngine` を1つ使った瞬間にこの検査は成立しない。
   - `TreatWarningsAsErrors` / `LangVersion 9.0` 固定(Unity 側より新しい言語機能を通さない)
   - `EnableDefaultCompileItems=false` + 2ファイルの明示指定。⚠️ **ワイルドカードにしない** ——
     将来 Unity 依存のファイルが増えたときに検査が黙って壊れるのを避ける
   - ⚠️ **`UNITY_IOS` 分岐も別に1回コンパイルする。** 生成物の
     `#if UNITY_IOS && !UNITY_EDITOR`(`__Internal` 静的リンク)は既定ビルドでは通らない枝で、
     `build.rs` のコメントにあるとおり過去に実際の iOS リンク失敗を生んだ箇所
2. **`csharp_abi_sync.rs` に `offset_of!` assert** —— `MwMusicPosition` /
   `MwOutputUnderrunStats` / `MwEvent` の全フィールドのオフセット + サイズ + アラインメント。
   加えて **判別子を運ぶ enum が4バイトであること**の assert
   (`#[repr(i32)]` を外すと Rust はサイズを自由に選べる。`MwEventKind` が1バイトになっても
   `payload` は 8 に揃うのでオフセット assert では捕まらないが、C# が `int` として
   読む4バイトのうち3バイトがゴミになる)
3. **`make csharp-check`** を `make lint` へ組み込み(約3秒。コーヒー基準を壊さない)。
   CI は `lint-test` ジョブの **`cargo test` の後**に置く —— 検査対象の
   `NativeMethods.g.cs` は `build.rs` の成果物でリポジトリに無いため。
   📌 Makefile と CI で同じ検査を二重に書かないため、CI は `make csharp-check` を呼ぶだけ

📌 モジュール doc の「二重の防御」を **「三重の防御」** に書き換えた(コンパイル時の
非網羅 `match` / 実行時の enum 突き合わせ / **レイアウト**)。

## P3-12 —— 予約 SE のオーバーフロー件数を FFI へ出した

カウンタ自体は前に `Renderer` から `Mixer` へ移して本番経路で加算されていたが、
**FFI に出ていないので Unity 側からは読めなかった**(「半分だけ進んだ」状態)。

🔴 **`mw_se_schedule` は予約が捨てられても `Ok` を返す。** コマンドキューへ積めた時点で
成功なので、音声スレッドが予約キューへ挿入する段で満杯だったことは呼び出し側へ伝わらない。
**読む口が無い限り「メトロノームがたまに抜ける」を誰も観測できない。**

- `Mixer::se_schedule_overflow_count` を `Arc<AtomicU64>` にし、
  `se_schedule_overflow_counter()` で複製を取れるようにした(`Renderer` も委譲)。
  ⚠️ 音声スレッド側の操作は `fetch_add`(Relaxed)のままで、アロケーションもロックも
  増えない(『§5.3』のリアルタイム安全性規約)
- `Instance` が複製を保持。🔴 **`Backend::open` へムーブする前に取る**(ムーブ後は `Mixer` に触れない)。
  ⚠️ `attempt_reopen` は `Mixer` ごと作り直すので**そこでも差し替える** ——
  忘れると誰も増やさない古いカウンタを読み続けて「ずっと 0」に見える
- `MwOutputUnderrunStats` に1フィールド追加(**24 → 32 バイト**)

### 🔴 名前と中身が合わなくなる件をどう扱ったか

`MwOutputUnderrunStats` の doc は「フィールドは `Backend` の3つに 1:1 で対応する」と
書いてあった。ミキサ由来のカウンタを足すとこれが崩れる。

**構造体の位置づけを言い直して受け入れた**:
「**音声スレッド側で黙って失われたものを、ゲームスレッドが1回の呼び出しで拾う口**」。
用途(毎フレームの診断ポーリング)も要求(GC アロケーションゼロ)も同じで、
カウンタ1本のために P/Invoke をもう1回増やすほうが割に合わない。
⚠️ **doc に「足してよいものの基準」を明記した** —— これが無いと、この構造体は
雑多な診断値の置き場になる。

### 古い案内を2箇所直した

`ffi.rs` の `mw_se_schedule` doc と `MwNative.ScheduleSe` doc が、どちらも
`mw_core::Renderer::se_schedule_overflow_count` を「検知できる場所」として案内していた。
🔴 **`Renderer` は `Backend::open` へムーブされるのでゲームスレッドからは触れない。**
読めるのは FFI 経由だけなので、そう書き直した。

## P3-13 —— 曲切り替えで圧縮バイト列を丸ごと複製しなくなった

`mw-ffi` は音源ストレージに `Arc<Vec<u8>>` を持っているのに、
`SymphoniaDecoder::open` が `Vec<u8>` を値で要求するため `(*bytes).clone()` していた。
数十MB の ogg では曲を切り替えるたびにゲームスレッドで数十MB の `memcpy` が走り、
ピークメモリも倍になる。

- `mw-core` に **`SharedBytes`(newtype)** を足し、**`SymphoniaDecoder::open_shared`** を追加。
  🔴 **newtype が要るのは、`Arc<T>` が実装するのが `AsRef<T>` であって `AsRef<[u8]>` では
  ないため** —— symphonia の `MediaSource` は `impl<T: AsRef<[u8]> + Send + Sync> for Cursor<T>`
  なので、`Cursor<Arc<Vec<u8>>>` は満たさない。
  📌 `Arc<[u8]>` へ持ち替える案もあるが、`Vec<u8>` → `Arc<[u8]>` の変換自体が1回コピーで、
  呼び出し側の型も一緒に変える必要がある
- `open(Vec<u8>)` は `open_shared` への委譲として残した(既存テストの大半がこちらを使う)
- `mw-ffi` の3箇所(`mw_music_set` / `restore_music` / `restore_bgm`)を `open_shared` へ

### 🔴 `remove_music_bytes` の doc は書き直しが必要だった

あの doc は「再生中の楽曲を release しても安全」の理由を
**「複製しているのでデコードスレッドとは最初から別メモリ」**と説明していた。
これが**成り立たなくなる**。

いまは `Arc` の参照カウントで安全を担保している —— マップから外れても、デコーダが
保持している複製(`Arc` の複製であってバイト列の複製ではない)が生きている限り解放されない。
⚠️ **挙動の違いも書いた**: 「再生中の曲を release してもメモリがすぐには減らない」ことが
**ありうる**(曲を切り替えるかデコーダが落ちた時点で減る)。
数十MB の複製を毎回作るコストと引き換えに、これは受け入れる判断。

### 退行防止テストは参照カウントを直接見るしかない

⚠️ **複製に戻しても動きは一切変わらない** —— `total_frames` も読み出し結果も同じで、
変わるのは曲切り替えの所要時間とピークメモリだけ。だから
`Arc::strong_count` を直接見るテストを入れた。
**変異(`open_shared` を複製へ戻す)で落ちることを実測済み。**
