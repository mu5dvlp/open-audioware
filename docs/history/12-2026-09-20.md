### どこが欠けていたか(実測で特定した)

Codecov の未到達行は **1145 行**で、**そのうち 764 行(67%)が `ffi.rs`** だった。原因は1つ:

`ffi.rs` の統合テスト一式(SE / イベント / 楽曲 / プレビュー連打 / BGM / 再オープン。
**約830行**)が `init_se_lifecycle_then_shutdown_or_gracefully_reports_no_device` の
**`mw_init` が成功したときだけ**走る鎖になっており、デバイスの無い CI では

### 🔴 「開けたふりをするだけの fake」では通らなかった

前節で入れた `FakeBackend` は `Renderer::render` を呼ばない。**`mw_music_state` が
`Ready` を返すのも `mw_music_get_position` が進むのも `mw_bgm_state` が変わるのも、
すべて `Renderer::render` の中で `MusicClockPublisher::publish` /
`BgmStatePublisher::write` が呼ばれることによる**(`mixer.rs::render` 末尾)。
レンダラが回らなければ状態は永久に `Loading` で、`wait_until(..., 5s)` が全部タイムアウトする。

⇒ **仮想オーディオデバイス**(`test_backend::VirtualBackend`)を作った。`open()` で
「音声スレッド相当」を1本立て、`Renderer::render` を**実ホスト時刻つきで、実時間の歩調で**
回す。`close()` / `Drop` のどちらからでも停止・join する。

設計で外せなかった点(どれも踏んでから直した / 踏まないよう先に決めた):

| | なぜそうしたか |
|---|---|
| **歩調は実ホスト時刻に追従させる**(固定 sleep で固定フレーム数を出さない) | CI の runner が混んでスレッドが飢えると、フレームクロックが実時間から遅れていき「位置が進むのを待つ」テストがタイムアウトする。遅れたぶんはまとめて取り戻す(実デバイスも OS が詰まればバッファを続けて要求する) |
| 🔴 **バッファ長は実デバイスと同じ固定 480 フレーム(10ms @48kHz)** | 「経過時間ぶんをそのまま render」にすると起動直後は 5 フレームで呼ばれ、`Instance::log_buffer_info_once` が **`5 frames @ 48000 Hz = 0.104 ms`** という**実機ではありえない値を「実測の I/O バッファ長」としてログへ出す**。このログは iOS の申告値を裏取りする唯一の手段なので、信用できる状態に保つ |
| **アンダーランは模擬せず 0 のまま** | 既存テストが `count == 0` と `last_host_time_ns == 0` の整合を見ている。片方だけ非ゼロにすると落ちる |
| **`make_backend()` のたびに新しい仮想デバイスを払い出す** | 再オープンの段2 が作る新バックエンドも駆動されないと、再オープン後に状態が二度と進まない |

⚠️ **実デバイス版のテストは置き換えていない。** cpal の実際のデバイスオープン・OS の
コールバック時刻・実機のレート交渉は、引き続き実デバイス版だけが通る経路。
仮想デバイス版が担うのは **FFI 境界から上のロジック**(引数検証・ハンドル管理・
コマンド列の順序・状態遷移・イベント通知・内部再オープン)。

### 残った 203 行の大半は「エラー型の `Display`」だった

🔴 **ここを固定した理由は数字ではない。** 実機で何が起きたかを知る手段がこのログしかない

  🔴 **ワイルドカード無しの `match` を通す**ので、バリアントを足すとテストが
  **コンパイルエラー**になる(`csharp_abi_sync.rs` と同じ手)。あわせて
  **(1) バリアント間で文言が重複していないこと**(コピペ事故の検出)、
  **(2) 引数つきなら引数が文言に出ていること**も見る

  配列の順番を変えたときに**別のバリアントを検査して偶然通る**(数字が他の文言に

- 🔴 `mw_music_set` / `mw_bgm_set` のエラー経路2本: **解放済み ID** →
  `ErrInvalidSoundId` / **壊れたバイト列** → `ErrDecodeFailed`。
  **Music モードはロード時にデコードしない**ので、壊れた入力はここで初めて弾かれる
  —— `docs/security/` の脅威モデルが気にする「壊れた/悪意ある入力」の経路そのもの

### なぜやったか —— 数字ではなく、**検証手段が無かった経路**のため

P3-11 で足した [`teardown_orphaned_reopen`](../../crates/mw-ffi/src/handle.rs) ——

# 🔴 P3-11(2026-09-23): 内部再オープンをロック保持のまま行わないよう3段構成へ分割

**リファクタ計画(`docs/plans/REFACTOR-PLAN.md`)の最後の1件、P3-11 を実装した。39項目中
39件完了(100%)。**

## 問題

`handle_registry::maybe_reopen`(`mw_poll_events` から毎フレーム呼ばれる)が、レジストリの
`Mutex` を保持したまま `Instance::attempt_reopen` を丸ごと実行していた——中身は
`backend.close()` → `stop_and_join_decode_threads()`(スレッド2本を join。待ち時間に上限無し)→
`Renderer::build_with_events()` → `backend.open()`(cpal のデバイスオープン。数百 ms かかりうる)→
`SymphoniaDecoder::open_shared`(デコード probe)。この間、他のすべての FFI 呼び出しが
ゲームスレッドで足止めされる——初期構築仕様『§5.4「全関数非ブロッキング」』への最悪の違反。

## 設計(ワークスペースの `docs/handoff/operations.md` 決定表で確定済み)

**再オープン中の API 呼び出しは「成功を返して捨てる」**(数百ミリ秒の SE 欠けは許容。
ブロックしない・専用エラーは作らない)。実装は3段構成:

1. **段1**(`Instance::begin_reopen`。ロック保持中): 復元用スナップショットを読み、重い部品
   (`backend`・デコードスレッドの `JoinHandle`)を `Instance` から切り離す。`self.backend` は
   新品の未オープン `CpalBackend` に、`decode_thread`/`bgm_decode_thread` は `None` になる。
2. **段2**(`run_reopen_worker`。専用のワーカースレッド上、ロック無し): 切り離した旧バックエンド・
   旧デコードスレッドを畳み、新しい `Renderer` 一式を組み立てて新バックエンドを開く。
3. **段3**(`finalize_reopen_success`/`finalize_reopen_failure`。再度ロック保持中): 段2 の結果を
   `Instance` へ差し込む。**ただし `Instance` の `handle` が段1で捕まえたものとまだ一致する
   場合に限る**——段2 の間に `mw_shutdown` が来ていれば(`Instance` が消えている/差し替わって
   いれば)、差し込まずに `teardown_orphaned_reopen` が自分で組み立てた新バックエンド・
   新デコードスレッドを畳んで捨てる(レジストリには一切触れない)。

**この間、`Instance` はレジストリに存在し続ける**——これが25箇所の FFI 呼び出しサイトを
1つも変えずに済ませる鍵。getter 系は段2の間「未オープンな `CpalBackend`」を読むだけなので
`Backend` トレイトが元々持つ「未オープンなら 0」の契約にそのまま乗り、コマンド系は
畳まれつつある旧 `Renderer` の受信側(rtrb)へ積むだけなので、相手が消えていても即座には
エラーにならず「成功を返して捨てる」がそのまま実現される。

### 二重起動を防ぐ進行中フラグ

`ReopenPolicy`(バックオフ判定)だけでは「段2 実行中に次のフレームがもう1回 `maybe_reopen`
を起動してしまう」ことを防げない(1回の試行の結果〔`record_result`〕は段3で初めて記録される
ため、段2の間は `is_due` が `true` のままになりうる)。そこで `crate::handle::REOPEN_IN_PROGRESS`
(`AtomicBool`、`Instance` のフィールドではなくモジュール static——レジストリの `Mutex` を
取らずに読める必要があるため)を追加し、`ReopenInProgressGuard`(RAII、`Drop` で必ず解除)で
段2〜段3の間ずっと立てておく。`panic = "unwind"` のままなので、段2内で万一パニックしても
`Drop` は必ず走り、フラグが立ちっぱなしで「詰む」ことはない。

### 唯一の実挙動変更: `backend_sample_rate()` のフォールバック

`Instance::backend_sample_rate()`(`mw_sound_load` のリサンプル判定、初期構築仕様『§4.7』)は
段2 の間 `self.backend.sample_rate() == 0` になってしまう。`Instance::last_known_sample_rate`
(`AtomicU32`。`init()`/段3成功時に書き込む)へフォールバックすることで解決した。
⚠️ **トレードオフを承知で受け入れる**: デバイスのレートが再オープンを挟んで実際に変わって
いた場合、段2の間にロードされた SE は「1つ前の」レートを前提にリサンプルされる——窓は数百 ms、
影響は「SE 1個がわずかに違うレートへリサンプルされる」だけ(クラッシュしない・再ロードすれば
直る)なので許容する。

### `mw_shutdown` の判断: 段2 の間の `CloseFailed` を `Closed` として報告する

段2 の間に `mw_shutdown` が呼ばれると、`instance.backend` は段1が置いた新品の未オープン
`CpalBackend` なので `close()` が `BackendError::NotOpen` を返す——これは「本当に閉じ損なった」
のではなく「段2の途中でたまたま検出した」だけなので、`CloseFailed` は誤解を招く。
[`is_reopen_in_progress()`] が `true` の間に限り `NotOpen` を `Closed` として報告するよう
`shutdown()` を変更した(旧バックエンドは段2側で既に/まもなく閉じられ、段2が組み立てた
新バックエンドは段3の「`Instance` が消えている」分岐が自分で畳む)。**再オープンが
失敗した直後(バックオフ待機中)の `NotOpen` は従来通り正直に `CloseFailed` のまま**——
この場合は `self.backend` が本当に「開けなかった」状態のままだからで、この挙動は
P3-11 以前から変えていない。

### 見つけた小さな綻び(意図的に直さなかった)

`mw_music_set`/`mw_bgm_set` が使う `decoder_tx`/`bgm_decoder_tx`(`mpsc::Sender`)は rtrb の
コマンドキューと違い、受信側(旧デコードスレッド)が段2で実際に `join()` され切った後は
`send` が失敗し、`MwResult::ErrCommandQueueFull` が返る——「成功を返して捨てる」の原則から
外れる。ただし**これは今回の分割が新たに持ち込んだものではない**: 再オープンが失敗した後、
次の自動再試行までの待機中にも(`self.decoder_tx` を差し替えないため)全く同じことが
以前から起きていた。今回増えたのは「その隙間が段2 の間(数百 ms)にも新たに生じる」ことだけ。
ブロックしない・新しいエラーコードを増やさない、という性質は変わらないため、依頼された
設計をそのまま実装し、対症療法(段2専用のダミー受信先への差し替え等)は複雑さが増すだけと
判断して見送った。

## 検証

`cargo fmt` / `cargo clippy --all-targets -- -D warnings` / `cargo test --workspace` は全緑
(mw-ffi 87 tests、既存の実機越し統合テスト `run_reopen_lifecycle` を含む——このマシンには
実オーディオデバイスがあり、実際に3段構成の非同期パスを通して再オープン成功まで確認できた)。

🔴 **ただし受け入れ確認は Android 実機が要る**(AAudio の切断→復帰)。デスクトップの
`cargo test` は「段2 の間、他の呼び出しがブロックされないこと」自体は測れない
(タイミングを検証する自動テストではなく、この環境のデバイスは cpal が同じデバイスへ
再オープンできてしまうため、Android の実際の切断シナリオの代わりにはならない)。
新規ユニットテストは `is_reopen_in_progress()`/`ReopenInProgressGuard`/`maybe_reopen` の
無効ハンドル経路という、ロック無しで読めるフラグの契約だけを固定化している——実装は
`crates/mw-ffi/src/handle.rs`(`Instance::begin_reopen`/`run_reopen_worker`/
`finalize_reopen_success`/`finalize_reopen_failure`/`teardown_orphaned_reopen`)。
