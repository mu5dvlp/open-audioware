# 作業記録 2026-09-29

## Miri を入れた(ADR-0003。fuzz / Miri / TSan の1段目)

ユーザー決定(2026-09-29)「Miri → cargo-fuzz → TSan の順。依存排除のステップ2(rubato)より前に Miri と
fuzz を終える」の1段目。`make miri`(CI と同じ範囲)/ `make miri-all`(mw-core 全体)/ CI の `miri`
ジョブを足した(`e56f6e4`)。nightly は `Makefile` の `MIRI_TOOLCHAIN`(`nightly-2026-09-27`)だけが
日付を持ち、CI は `make miri` を呼ぶだけ。

- **Miri が初回で本物の未定義動作を1件見つけた**: `ring_buffer.rs` の `slot()` が
  `(*cell.get()).as_mut_ptr()` で一瞬 `&mut MaybeUninit<T>` を作っており、`write_chunk` が第1区間の
  先頭として先に取った `first_ptr` の権限を、第2区間用の `slot()` 呼び出し(容量の先頭へ折り返す)が
  無効にしていた(Stacked Borrows)。`UnsafeCell::raw_get` で参照を経由しない形に直した。
  実機で症状は出ていなかったが、最適化次第で壊れうる形。
- **上流の未定義動作を1件踏んだ(直せない)**: rustfft(rubato → realfft の依存)の SSE 経路にある
  `_mm_load1_pd` が 4 バイト整列の `Complex<f32>` を 8 バイト整列として読む。
  `x86_64-apple-darwin` は SSE4.1 が既定で有効なので Mac でだけ選ばれる。Miri の解釈ターゲットを
  `x86_64-unknown-linux-gnu`(SSE2 まで。CI と同じ)に固定して回避した(`MIRI_TARGET`)。
- **Miri では対象外にしたテスト(理由は各テストの属性に記載)**:
  seqlock の並行テスト2件(Miri のスケジューラが書き手を書き込み途中で長く止め、`MAX_READ_RETRIES` を
  使い切って未整合を返す設計上の保険経路を常に踏む。全フィールドが atomic なので Miri のデータ競合
  検出の対象でもない)/ rubato の FFT を通すテスト6件(1本で数分〜十数分かかる。rubato を自前化したら戻す)。
- **所要(実測)**: CI の範囲(ring_buffer / wav / decode / stream)は **40 件 109 秒**。
  ring_buffer + mixer + stream + voice は 82 件 523 秒。全体(`miri-all`)は 30 分前後(mixer / music が
  音声を描画するため1件ずつ数十秒)。
- 通常の `cargo test --workspace` は **340 passed**、clippy / fmt 緑。
- **CI の `miri` ジョブは初回(sysroot のキャッシュ無し)で 2 分 16 秒**(ubuntu ランナー。コーヒー基準内)。全ジョブ成功。

## cargo-fuzz を入れた(ADR-0003 の2段目)—— 初回の 60 秒で本物を2件

`fuzz/`(workspace 外)に3本: `wav_decode`(`wav::decode`)/ `wav_decoder_pump`(`WavDecoder::open` →
`stream::channel` へ `pump`、`seek` / `read`)/ `resample`(`StreamResampler` と `resample_oneshot`)(`c4dcf68`)。
シードは `fuzz/seeds/make_seeds.py` が生成(`arbitrary` のバイト消費順に合わせてある)。
`make fuzz-corpus`(コーパスの回帰だけ。約3秒)を CI に、`make fuzz-run TARGET=… SECONDS=…` と
`fuzz-weekly.yml`(土曜 18:00 UTC、1本 900 秒)を長時間実行に。nightly は Miri と同じ
`NIGHTLY_TOOLCHAIN`(`MIRI_TOOLCHAIN` は別名で残した)。

- **見つかった1件目(`51b5853` で修正)**: rubato の `Fft::process_into_buffer` は NaN / inf を含む入力で
  **内部の `unwrap()` により abort** する(realfft の「Imaginary part of first value was non-zero」)。
  float32 の WAV の中身だけで踏め、`WavDecoder::read` → デコードスレッドに届く(スレッド側は
  `catch_unwind` で受けるので、プロセスは落ちずにストリームエラーになる)。`Result` では受け止められない
  ので、`deinterleave` で非有限を 0 に、絶対値 1e4 超を clamp する(`MAX_ABS_INPUT_SAMPLE`)。
- **2件目(同じコミット)**: `resample_oneshot(source_rate = 0, …)` が比 +inf のまま rubato の
  出力バッファを `usize::MAX` で確保しようとして abort。`StreamResampler::new` は rubato 側の検証で
  Err になっていたが `resample_oneshot` だけ素通しだった。両方の先頭に `validate_rates`
  (レート 0 と 256 倍超の比を `ResampleError::InvalidRates`)。
- 回帰用のクラッシュ入力は `fuzz/corpus/*/regression-*` に置き、`make fuzz-corpus` で毎回流す。
- **実測**: `fuzz-build` 初回 1 分 21 秒 / `fuzz-corpus` 約 3 秒 / 60 秒実行の速度は
  `wav_decode` 約 53〜92 exec/s、`wav_decoder_pump` 約 1,350 exec/s、`resample` 約 9 exec/s(FFT が実際に走る)。
  修正後は 3 本とも 60 秒でクラッシュなし。`cargo test --workspace` **351 passed**(mw-core +11)。
- `make miri-all`(mw-core 全体)は lib **195 passed / 8 ignored、763 秒**。
- **CI**: `fuzz` ジョブ 1 分 36 秒 / `miri` ジョブ 2 分 04 秒(sysroot キャッシュ後)。全ジョブ成功。
