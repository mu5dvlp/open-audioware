#### 2026-08-31(middleware: M3 最後の残り —— Android(AAudio)切断復旧の設計調査。**実装せず判断待ちで停止**)

**症状**(依頼書より): Android で Bluetooth 機器を切る等でオーディオデバイスが切断されると、
音が戻らない。iOS の割り込み・ルート変化復帰(`ios_interruption.rs`)・アンダーラン検知は
M3 として完了済みで、M3 の残りはこれ1件。

**進め方の指示どおり、実装の前に3つを実読で確認した(推測・ドキュメントではなくソース)。**

**1. iOS の復帰がどう実装されているか**(`ios_interruption.rs`)——`CpalBackend` は
`Arc<cpal::Stream>` を保持し、OS 通知(割り込み・ルート変化・バックグラウンド遷移)を
受けて**同じ `cpal::Stream` に対して** `pause()`→`play()` を呼び直す。効く理由:
cpal 0.18.1 の iOS 実装の `playing` フラグが OS 主導の停止に追随しないだけで、
CoreAudio 側の `AudioUnit` 自体は生きたまま——`Renderer` の所有権は一切動かさない
(コールバッククロージャに元々ムーブ済みのまま)。だから復帰してもボイス・バス音量・
楽曲位置が保持される。

**2. cpal の AAudio ホストが切断をどう通知するか**——`~/.cargo/registry/src/.../
cpal-0.18.1/src/host/aaudio/mod.rs::build_output_stream` の `error_callback` と、
`~/.cargo/registry/src/.../ndk-0.9.0/src/audio.rs::AudioStreamBuilder::error_callback`
のドキュメントを実際に読んで確認した:

- ndk 0.9.0 は `AAudioStreamBuilder_setErrorCallback` を薄くラップしているだけ。ドキュメント
  に明記:「The `error_callback` will be called, for example, if a headset or a USB device is
  unplugged causing the stream's device to be unavailable or "disconnected"」「In response,
  this function should signal or create another thread to stop and close this stream. ...
  **Do not stop or close the stream, or reopen the new stream, directly from this callback**」
- `AudioError::Disconnected`(`AAUDIO_ERROR_DISCONNECTED`)のドキュメントはさらに明確:
  「**The stream cannot be used after the device is disconnected.** ... Applications should
  stop and close the stream」——**AAudio の切断は API 契約として終端的であることが
  Google 自身のドキュメント(ndk クレートがそのまま転記したもの)に明記されている**。
  推測ではなく一次情報。
- cpal 側の変換(`cpal-0.18.1/src/host/aaudio/convert.rs::impl From<AudioError> for
  Error`)は `Disconnected | Unavailable | NoService | InvalidHandle` を
  `ErrorKind::DeviceNotAvailable` へ丸めている。この `ErrorKind` は本クレートの
  `err_fn`(`cpal_backend.rs::build_output_stream` の `err_fn` = M2-6 から存在する
  一般エラー通知経路。iOS のルート変化 `StreamError` と全く同じ配線)へそのまま渡る。
  **つまり Android の切断通知そのものは、新しいコードを一切足さなくても既に
  `Event::StreamError { reason: DeviceUnavailable }` として `mw_poll_events` 経由で
  観測できている**(`cpal_backend.rs::classify_stream_error` が
  `ErrorKind::DeviceNotAvailable → StreamErrorReason::DeviceUnavailable` へ変換する、
  既存コード)。ここは前任者の 2026-08-28 の点検結果(`docs/history/01-...md`)と
  一致する再確認。

**3. 「`Renderer` をコールバックから取り戻せない」の実体をコードで確認**
(`backend.rs`/`cpal_backend.rs`/`mw-core/src/renderer.rs`)——

- `Backend::open(&mut self, renderer: Renderer, events: Arc<EventQueue>)` は `Renderer` を
  **値渡し(ムーブ)**で受け取る契約(`backend.rs`)。
- `CpalBackend::open` はこれを `build_output_stream(&device, &config, renderer, ...)` へ渡し、
  その中で `move |data, info| { ... renderer.render(...) }` というクロージャへ**さらに
  ムーブ**する。このクロージャは `device.build_output_stream(...)` に渡り、cpal 内部で
  `Box<dyn FnMut>` として保持される(cpal のどのホスト実装にも、ビルド済みクロージャの
  捕獲状態を後から取り出す API は無い——ソース上、`Stream`/`Device` 型はクロージャを
  一切外部へ再公開しない)。
- `CpalBackend` 自身が持つのは `Option<Arc<cpal::Stream>>` だけ(`pause()`/`play()` を
  呼び直すためのハンドル)。`Renderer` への参照は最初から一度も持っていない。
  `CpalBackend::close()` は `stream.pause()` → `drop(stream)` するだけで、**`Renderer` を
  返す経路がそもそも存在しない**——ここは「取り戻す手段を実装し忘れている」のではなく
  「設計上、返す先が無い」。
- `mw_core::Renderer::build(config, sample_rate)` はミキサ・ボイスプール・バス・
  コマンドキュー受信側・音楽クロック発行者(`Arc<MusicClockPublisher>`)を**まとめて
  新規生成**する(`renderer.rs`)。したがって「閉じて作り直す」を今の設計のまま行うと、
  新しい `Renderer::build()` を呼ぶ以外に道が無く、ボイス・バス音量・楽曲再生位置が
  まるごと初期状態に戻る。これは 2026-08-28 の iOS 対応時に見送られた「案1」と
  完全に同じ壁(`ios_interruption.rs` 冒頭 doc「実装方針」参照)——**推測ではなく
  今回コードを辿って再確認した事実**。

**iOS の形が Android で使えるか: 使えない。** iOS の復帰が効くのは「`cpal::Stream`/
`AudioUnit` 自体は生きていて、cpal 側のフラグ管理がズレているだけ」だから。AAudio の
切断は違う——`AudioStream` ハンドルそのものが ndk/AAudio の API 契約上使用不能になる
(上記2番)。**同じ `cpal::Stream` に対して `pause()`→`play()` を呼び直す設計は
Android には原理的に適用できない**——ここは実機を待たずソースの記述だけで確定できた。

**初期構築仕様を読み直すと、この状況は元々想定済みだった。** §6(【確定】)に
「ストリーム自体の切断(AAudio の disconnect 等)は**ミドルウェア内部で再オープンし、
イベントで通知する**」とあり、§4.4(【確定】)の音楽クロックには「シーク・停止・
**再オープン(ルート変化)**で不連続が起きるたびに」インクリメントする `generation`
(世代カウンタ)が最初から設計されている(`mw_core::clock::MusicClockPublisher::
bump_generation` として実装済み・テスト済み)。§14 のリスク表はさらに踏み込んで
「**再オープン中の曲位置は内部カウンタで継続**」と書いている——つまり「閉じて作り直したら
全部失っていい」がそもそも仕様の想定ではない。

**ここで判断が要ると判断し、実装を止めた。** §6/§4.4 の設計をそのまま実現するには、
`crates/mw-ffi/src/handle.rs::Instance` が固定フィールドとして持っている
`command_sender` / `reclaim_receiver` / `music_clock`(`Arc<MusicClockPublisher>`)/
`bgm_state` / 各デコードスレッドのハンドル一式を、**`Renderer::build()` の再実行ごとに
差し替え可能**にする必要がある(今は `Instance` 構築時に一度だけ作って以後固定)。
これは 2026-08-28 に「今回のスコープを超える」として見送られた「`mw-ffi::handle::
Instance` 側の大きな再設計」(初期構築仕様§14 が「M3 で必須実装」と呼ぶ本丸)そのもの
であり、今回あらためて `Instance` の実装を読んでも同じ結論になった——`Backend` の
シグネチャ変更に留まらず `mw-ffi` 全体に波及する変更で、依頼書が明示した「広い変更に
なる場合は報告して指示を待つ」に該当すると判断した。安全網が別の未検証の前提に
乗っていたことが3回(R12/R13/R24)続いたワークスペースでもあるため、「たぶんこう
すれば戻る」で `Instance` の所有モデルへ手を入れることは避けた。

**検討した選択肢(指示待ち)**:

- **案A(仕様どおり): ミドルウェア内部で完全再オープン。** `Event::StreamError

#### 2026-08-31(middleware: M4 終了条件「選曲プレビューのネイティブ化」—— 既存の `mw_music_*` がそのまま口になることを確認)

**M4 の残タスク「選曲プレビューのネイティブ化」に着手し、結論として新しい FFI /
C# ラッパは一切足していない。** 既存の `mw_music_*`(唯一の楽曲ボイス、M2-7)が
そのまま「選曲プレビュー用の口」であり、これは思いつきではなく初期構築仕様
`§3`/`§4.3` に**既に明記されていた**設計(`mw_music_set_loop` の doc コメントに
「選曲プレビュー用、フェードイン/アウト付き」と直書きされている)。今回やったのは
その口が実際にクライアントの使い方に耐えるかを検証し、根拠となる回帰テストを足すこと。

**まず M4-3(BGM のネイティブ化)のコミットを読み、踏襲できるか判断した**
(`02-2026-08-29--2026-08-30.md` の同エントリ参照)。BGM は「メタ画面向けの2本目の
楽曲ボイス(クロック無し)」であり、選曲プレビューとは動機が異なる。BGM 追加時の
判断基準(M14「クロックの発行元は1本目に固定」)に照らすと、**プレビューは1本目の
楽曲ボイス(`music_voice`)を再利用すべきで、BGM 用の2本目を流用すべきではない**
と判断した。根拠:

- 初期構築仕様 `§3`「作るもの」/ `§4.3`「楽曲再生」が「ループ区間設定(選曲プレビュー
  用。フェードイン/アウト付き)」を**楽曲再生の機能**として明記している(BGM が
  実装される M4-3 より前からある記述)。`mw_music_set_loop`(`crates/mw-ffi/src/
  ffi.rs`)の doc コメント自体が「選曲プレビュー用」と名指ししている。
- 選曲プレビューは Live 開始前(メタ画面)にのみ起こる操作であり、その時点で
  `music_voice`(Live 中に判定対象になる曲を鳴らす、唯一クロックを持つボイス)は
  常に未使用。Live を開始すれば `mw_music_set` が同じ Prepare→Seek のリセットで
  プレビューの状態を上書きするので、衝突しない。
- 逆に BGM ボイスをプレビューに転用すると、メタ画面のループ BGM(タイトル曲等)と
  選曲プレビューが同時に鳴らせなくなる(BGM ボイスは1本しか無いため)。`music_voice`
  を使えばこの制約が生じない——両者は別ボイスなので同じ Bgm バス上で単純に加算されるだけ
  (M4-3 のクロスフェード設計と同じ理屈)。

**クライアント側(`music-game-client-template`)の現状を読んで確認した(読むだけ、
1文字も書き換えていない)**: 選曲ページのプレビュー再生は**まだ実装されていない**
(`AudioSource` ベースの実装コードも見当たらなかった。`LiveScreenPresenter`/
`LiveScreenView` の曲選択ハンドラ〔`SelectSong`〕は現状ハイスコア表示とジャケット
更新のみで、音声再生には一切触れていない)。依頼書の「まだ Unity の AudioSource に
残っている」は今後実装される前提の記述と理解した。一方 `NativeMusicClock.cs`
(`App.Audio.Native`)は既に `mw_music_set`/`MusicPlayScheduled`/`MusicSeek`/
`MusicSetLoop` 等を Live 本編の楽曲再生で使っており、C# ラッパ(`Mw.Native.MwNative`)
側の口はすべて揃っている。よってプレビューの実装はクライアント側の今後の作業で、
今回のスコープ(open-audioware 側)は「口が実際に安全に使えることの検証」に絞った。

**「プレビューは BGM と何が違うのか」を依頼書の想定差分ごとに確認した:**

- 曲の途中から再生する → `mw_music_seek(handle, frames)` で既に可能。
- フェードイン・アウトする → `MusicVoice::play`/`stop`/ループ折り返しは既定ランプ
  経由(M13)。新規実装は無い。
- ループする → `mw_music_set_loop`(まさにこれのための API)。
- 選曲を変えるたびに素早く切り替わる/ロード中に切り替わる → 下記参照。
- 音量が本編と別 → **これは実際には成立しない**と確認した。`music_voice` と
  `bgm_voice` は既に**同じ Bgm バス**を共有する設計(M4-3, `mixer.rs::Mixer::render`
  の `bgm_gain` 適用箇所)で、固定4バス(Master/Bgm/Se/Voice)以外は増やさない
  という `§4.1` の方針にも合う。プレビュー専用バスを新設する理由は無い。

**🔴「連続切り替え」「ロード中の切り替え」への対策(依頼書 R38 への警戒)**:
新しく何かを実装したわけではなく、**M2-7 で `mw_music_set` に既に組み込まれていた
設計がこの要件をそのまま満たしていることを確認し、回帰テストで固定化した**。

- `crates/mw-ffi/src/decode_thread.rs::spawn` のデコードスレッドは、mpsc チャネルに
  複数のデコーダが溜まっていれば**最新のものだけを採用する**(`while let Ok(next) =
  rx.try_recv() { current = Some(next); }`)。連打で `mw_music_set` を呼んでも、
  古いデコーダは一度も pump されずに `Drop` されるだけで、詰まったり順序が入れ替わって
  古い曲が鳴ったりしない。
- `mw_music_set` は毎回「デコーダ差し替え → `MusicPrepare` → `MusicSeek{0}`」を送る。
  `MusicPrepare`(`MusicVoice::prepare`)はゲインを**ランプ無しで即座に 0** に落とし
  状態を `Loading` へ戻す(`music.rs::MusicVoice::prepare` 参照)。`render()` は
  `Loading` 中は先頭で無音初期化した出力をそのまま返す(`music.rs::MusicVoice::
  render` 冒頭の `for sample in out.iter_mut() { *sample = 0.0; }`)ため、**前の曲の
  PCM が漏れる余地が構造的に無い**。R38(クライアント側 SE 実装の「ロード中は無言で
  スキップ」)のように状態が `Loading` のまま固まる経路も無い——`MusicPrepare` は
  無条件遷移であり、待ち合わせやフラグの持ち越しが無いため。
- これらはいずれも M2-7 時点の実装(BGM 追加より前)であり、BGM(M4-3)は
  `decode_thread::spawn` をそのまま2本目として使い回しただけ。つまり「BGM で
  確認済みの安全性」は実は「M2-7 の楽曲ボイスで先に確立され、BGM が踏襲した」もの。

**足したテスト**(いずれも新しい実装ではなく、既存の口を「プレビューの実際の使われ方」の
形で通す回帰テスト):

  まま〕——理由はグローバルレジストリとデコードスレッドがプロセス内で1本しか
  立てられないため、`run_music_lifecycle`/`run_bgm_lifecycle` と同じ設計に揃えた)。
- `render_path_never_allocates_or_deallocates`: 単独 30 回連続実行で 0 失敗
  (`cargo test -p mw-core --test realtime_safety -- --test-threads=4

  テストコードのみ**(`mixer.rs`/`ffi.rs` の `#[cfg(test)] mod tests` 内、および

**ついでに直した既存のドキュメント誤り**: `mw_music_set` は現在
「デコーダ差し替え → `MusicPrepare` → `MusicSeek{0}`」の**2コマンド**しか送らない
(`MusicStop` は不要な no-op のため送信側から既に省かれている)が、
`crates/mw-core/CLAUDE.md` / `crates/mw-ffi/CLAUDE.md` / `mixer.rs` の
`music_set_command_sequence_recovers_cleanly_from_a_song_still_playing` の doc
コメントが「3コマンド(`MusicStop` を含む)を送る」という古い記述のままだった
(おそらく `MusicStop` を省く簡略化が入った際にコメント更新が漏れた)。実装は
2コマンドのまま(テストは「`MusicStop` を挟んでも安全」という不変条件を守るため
意図的に送り続けている)。3箇所とも記述だけ現状に合わせて修正した。

**クライアント側が移行するために何をすればよいか(引き継ぎメモ)**:

1. 新しい FFI は無い。既存の `Mw.Native.MwNative`(`unity/Runtime/MwNative.cs`)の
   `SetMusic(handle, soundId)` / `GetMusicState(handle, out state)` /
   `MusicPlayScheduled(handle, hostTimeNs)` / `MusicSeek(handle, frames)` /
   `SetMusicLoop(handle, beginFrames, endFrames)` / `ClearMusicLoop(handle)` /
   `MusicStop(handle)` をそのまま使う。
2. 「今すぐ再生」したいだけなら `MusicPlayScheduled(handle, MwNative.HostTimeNs())`
   でよい(`host_time_ns <= buffer_start_ns` は「発見可能な最速のサンプルで即座に
   発音」として扱われる、`mixer.rs::MusicSchedule::take_due_offset` 参照)。
3. 曲を選ぶたびに `SetMusic` → `GetMusicState` を `Ready` になるまでポーリング →
   （必要なら `MusicSeek` で試聴開始位置へ）→ `SetMusicLoop` でプレビュー区間を
   設定 → `MusicPlayScheduled` で再生、の順でよい。連打への配慮は不要——`SetMusic`
   を呼ぶたびに前の曲は即座に無音へ切り替わり、デコードスレッドは自動的に最新の
   要求だけを反映する(今回の回帰テストで固定化済み)。
4. **注意点は1つだけ**: Live 開始(`NativeMusicClock`)も同じ `music_voice` を使う。
   選曲画面から Live 画面へ遷移する際は、プレビューの `SetMusic`/`SetMusicLoop` の
   後始末(呼び出し側で `MusicStop`/`ClearMusicLoop` を呼ぶ、または Live 側の
   `SetMusic` 呼び出しがどうせ Prepare→Seek で上書きするので放置してもよい)を
   どちらにするかだけ、クライアント側の実装方針として決めること——ネイティブ側は
   どちらでも壊れない設計になっている。
5. メタ画面の BGM(タイトル曲等、`mw_bgm_*`)とプレビューは別ボイスなので、
   両方を同時に鳴らしたい場合もそのまま共存できる(同じ Bgm バスに乗るだけ)。

**判断に迷い、勝手に確定させなかった点**:
- クライアント側でプレビュー実装が「今すぐ再生」に `MusicPlayScheduled +
  HostTimeNs()` の組み合わせを使う設計になるか、それとも BGM のような単純な
  `PlayBgm()` 相当の口が欲しくなるかは、実際にクライアント側の実装が始まってから
  でないと分からない。今回は「既存の口で機能的に足りる」ことは確認したが、
  「使い勝手として十分か」はクライアント実装者の判断に委ねる(足りないと分かれば、
  `mw_music_play(handle)`〔`mw_bgm_play` と同じ非スケジュール即時再生〕を1つ足す
  だけで解決できる設計になっている——`MusicVoice::play()` は既に `Ready` からの
  即時再生をサポートしており、`Command::MusicPlayScheduled { host_time_ns: 0未満
  相当}` を経由しない直接呼び出しの配線を足すだけで済む)。
- 選曲プレビュー用のループ区間の具体的な長さ・フェード時間(既定ランプ 5ms〔M13〕を
  そのまま使うか、プレビュー用に長めのフェードにするか)はクライアント側 UX の
  決定事項であり、ネイティブ側は `mw_music_set_loop` の区間と既定ランプ以外に
  パラメータを持たない。プレビュー専用のフェード時間が要るなら `mw_bus_fade`
  (Bgm バス全体のフェード、既存 API)で代替できるはずだが、確認していない。
