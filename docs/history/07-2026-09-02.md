## リファクタ Phase 0 —— P0-4b(2026-09-04)

`26cf912`(P0-4)の調査時点で見つかっていながら指示範囲外のため未対応のまま
残っていた「もう1箇所」を直した。コミット: `cb097fc`。

**何が起きていたか**: P0-4 は自然終了(PCM 終端到達)側で
`position_frames=0` + `source.request_seek(0)` + `discontinuity=true` の
3点セットを入れて直したが、`stop()` 側は `position_frames=0` しかしておらず
`source.request_seek(0)` を呼んでいなかった。`position_frames` だけ 0 に戻しても
`StreamingMusicSource` のリングバッファ/デコーダのカーソルは停止直前の位置に
取り残されたままなので、**`stop()` → `play()` の鳴らし直しが曲頭からではなく
停止した位置の続きから鳴ってしまう**可能性があった。

**確定経路が2つあり、どちらも直した**:

- `Playing` 中の `stop`(フェードアウト後、`MusicVoice::render` 内の
  `PendingTransition::Stop` 分岐で確定): `render` の引数として `source` を
  既に持っているので、そこに `source.request_seek(0)` を足すだけで済んだ。
- `Paused` 中の `stop`(`render` を経由せず `MusicVoice::stop()` 自身の中で
  即座に確定): このメソッドはそもそも `source` を引数に取らないシグネチャ
  だったため呼びようが無かった。`seek`/`resume_at` と同じ形で
  `source: &mut dyn MusicFrameSource` を受け取るようシグネチャを変更した。
  呼び出し側は `mixer.rs::Mixer::apply_command` の `Command::MusicStop`/
  `Command::BgmStop` の2箇所のみで、どちらも `self.music_source`/
  `self.bgm_source` を既に持っているため配線を足すだけで済んだ。
  **FFI 境界には影響しない**——`mw-ffi` は引数無しの `Command::MusicStop`/
  `BgmStop`(unit variant)をコマンドキューへ積むだけで `MusicVoice::stop` を
  直接呼ばない。`mw_music_stop`/`mw_bgm_stop` のシグネチャ・`Command` の
  判別子とも変更無し。

**テストで「曲頭から鳴る」をどう確かめたか**: P0-4 のテストは `FakeSource`
(値が位置に依存しない `ConstantDecoder`/`FiniteDecoder` 相当)だったため、
今回は「実際に曲頭から鳴っているか」を PCM の値そのものから確認できる
`PositionEchoDecoder`(読み出しカーソルの値をそのまま PCM として返す新設
フェイクデコーダ)を `mixer.rs` に追加した。実際の
`StreamingMusicSource`/`MusicStreamProducer`(エポック ack のシーク調停を
実際にまたぐ)を介した経路で、`MusicVoice`/ゲインを経由せず
`source.read()` を直接呼び、「リングバッファに実際に積まれている PCM が
曲頭のものか」をランプの影響を受けずに判定している
(`music_stop_while_playing_then_play_again_replays_from_the_start` /
`music_stop_while_paused_then_play_again_replays_from_the_start`)。
修正前はどちらも失敗することを確認済み(コミット前に一時的に修正を戻して
再現させた)。`music.rs` 側にも `FakeSource` レベルの単体テストを3本追加した。

**検証**: `cargo test --workspace` 297件(mw-backend 35 / mw-core 184 /
realtime_safety 2 / mw-ffi 76、doctest 0)全緑・clippy(host、
`--workspace --all-targets -D warnings`)・fmt --check 通過。
`cargo clippy --target aarch64-apple-ios` は mw-ffi の Android 再オープン系
(`handle.rs`/`reopen.rs`、M3)が dead_code 扱いで失敗するが、これは
このコミット適用前の `main` でも同一に失敗する pre-existing の問題
(今回の変更はどちらのファイルも触っていない、`mw-core` 止まり)。

🔴 **ネイティブバイナリの再ビルドが必要**(mw-core の変更なので dylib /
xcframework / so の3種とも)。今回の変更は既存関数のロジック差し替えのみで
シンボル名・エクスポート関数の増減が無いため、`nm`/`strings` で新旧を機械的に
見分けられる根拠は無い(`request_seek` はインライン化されうる小さな呼び出しで、
実行時の動作としてしか確認できない)。再ビルド後は
`crates/mw-core/src/mixer.rs` の `music_stop_while_playing_then_play_again_replays_from_the_start`/
`music_stop_while_paused_then_play_again_replays_from_the_start` と同じシナリオ
(楽曲を再生 → 途中で `mw_music_stop` → `mw_music_play_scheduled` で鳴らし直す)を
**実機/実デバイスで聴感確認**するのが唯一の確認手段。

#### 2026-09-02(SE ボイスのループ再生を追加 —— ホールド保持音の「出力経路が違う」問題の一部を埋める)

**背景**: ユーザー実機報告「ホールドの音の発生が遅い(継続音の方)」。オーケストレータが
測定で切り分け済み——音源ファイルの先頭ラグ・再生ロジックのバグはどちらもシロ。
残った本命は**出力経路そのものが違う**こと: タップ SE はミドルウェア(低レイテンシ)、
ホールド保持音は Unity の `AudioSource`(ミドルウェアの SE ボイスにループが無いため)。
クライアント側 `NativeAudioService.SetLoopPlaying` には「ミドルウェア側にループ付きの
SE ボイスが入ったら、ここを差し替えるだけで経路を戻せる」というコメントが既にあった。

**本作業のスコープ**: ミドルウェア側にループ付き SE ボイスを実装するところまで
(open-audioware リポジトリの担当分)。**クライアント側の実際の切り替え
〔`NativeAudioService.SetLoopPlaying` の差し替え〕は別リポジトリの作業であり
スコープ外**——今回の変更だけではユーザー体感は変わらない。

**実装**:

- `crates/mw-core/src/voice.rs`: `Voice` にループ区間 `Option<(u64, u64)>` を追加し、
  `VoicePool::set_loop(voice_serial, region)` / `VoicePool::loop_region(voice_serial)` を
  生やした。折り返しは `Voice::next_frame` が位置を読む直前に「終了フレームへ到達したら
  開始フレームへ巻き戻す」だけの単純な実装(排他的境界。`MusicVoice` の `cap_by_loop` と
  同じ考え方)。
- `crates/mw-core/src/command.rs` / `mixer.rs`: `Command::SetVoiceLoop { voice_serial, region }`
  を追加し、`Mixer::apply_command` から `VoicePool::set_loop` へ配線しただけ
  (`MusicSetLoop` の配線と同じ形)。
- `crates/mw-ffi/src/ffi.rs`: `mw_voice_set_loop(handle, voice, begin_frames, end_frames)`。
  `mw_music_set_loop`/`mw_bgm_set_loop` と**完全に同じ規約**——`(0, 0)` はループ解除
  (`LOOP_CLEAR_SENTINEL` を再利用)、それ以外で `begin >= end` は
  `MwResult::ErrInvalidLoopRegion`。
- `unity/Runtime/MwNative.cs`: `MwNative.SetVoiceLoop` / `MwNative.ClearVoiceLoop` を
  `SetMusicLoop`/`ClearMusicLoop` と同じ形で追加。**Rust 側だけ実装して C# ラッパを
  忘れる事故(`3991269` で構造的に塞いだはずの穴)を再び起こさないよう、実装の最初の
  一歩として先に追加した。**

**`MusicVoice::set_loop` と揃えた点 / あえて変えた点**:

- 揃えた: 区間の与え方(`(開始, 終了)` の組、終了は排他的境界)、`start >= end` の
  不正な区間はループ無しへ丸める(パニックしない)、解除は `None`。FFI 境界での
  `(0,0)` = 解除・それ以外の不正区間はエラーという規約も完全に同じ。
- 変えた: **折り返しにクロスフェードを挟まない。** `MusicVoice` の選曲プレビュー用
  ループは任意の位置がループ点になりうるため、既定ランプでフェードアウト→
  フェードインしてクリックノイズを消す。一方 SE のループはホールド保持音のような
  「素材自体がループ点で連続するように作られている継続音」を想定しており、単純に
  位置を巻き戻すだけにした(`voice.rs` の音量 `Ramp` は明示的な `stop`/スティールの
  フェードアウト専用のまま、ループ折り返しには一切使わない)。

**テスト**(279 → 289件、`cargo test --workspace`):

- `voice.rs`: 区間の設定・解除・不正区間の拒否・未知/フェード中ボイスへの無視・
  **ループ境界をまたいで正しくサンプルが出ること**(`indexed_sound` フィクスチャで
  フレーム番号をサンプル値に埋め込み、巻き戻り後の値を直接検証)・ループ中は
  データ長を超えても自然終了しないこと、の6件。
- `mixer.rs`: `Command::SetVoiceLoop` がコマンドキュー経由で実際に配線されている

  ⚠️ 実装中、このテストのフィクスチャに素の値(0..frames)をそのまま振幅として

- `crates/mw-ffi/src/ffi.rs`: `mw_voice_set_loop` の区間検証(`mw_music_set_loop` の
