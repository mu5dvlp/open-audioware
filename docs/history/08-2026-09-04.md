## リファクタ Phase 1 —— FFI 層の重複削減(P1-6 / P1-7)

`REFACTOR-PLAN.md` の P1-6(29関数中19が同型の15〜20行)と P1-7(`mw_music_*` /
`mw_bgm_*` がほぼ完全重複)。**内部実装だけのリファクタで、公開 FFI の面は不変。**

### P1-6

`crates/mw-ffi/src/ffi.rs` に2つのヘルパを入れた:

- `guarded(on_panic, f)` —— `catch_unwind(AssertUnwindSafe(...))` の唯一の場所。
  29関数がここを通る。
- `send_command(handle, build, on_sent)` —— 「ハンドルを引く → コマンドを1つ送る →
  結果を写像する」形(14関数)。`on_sent` は**送信成功時だけ**発火し、
  「コマンドキューが満杯のときは `note_bus_volume` / `note_track_loop` のキャッシュを
  更新しない」という既存の規則を保つ。
- `parse_loop_region` —— `(0,0)=解除 / begin>=end=拒否` の検証(3箇所コピペ)を集約。
- `From<WavError>` / `From<DecodeError>` for `MwResult` を `result.rs` に。
  `load_se` / `mw_music_set` / `mw_bgm_set` に重複していたエラー写像が1箇所になる。

### P1-7

`handle.rs` に `pub(crate) enum MusicTarget { Music, Bgm }` と `Instance` 側の振り分け
(`send_decoder_for` / `note_track_set` / `note_track_loop` / `track_state`)を足し、
**set / state / stop / set_loop の4組**を実体共有にした。公開関数は1〜3行のラッパになり、
元の doc コメントはそのまま残している。

⚠️ **畳む前に1行ずつ突き合わせて差分を洗い出した。以下は意図的に畳んでいない**:

- `mw_music_pause` / `resume_at` / `seek` / `play_scheduled` / `get_position` と
  `mw_bgm_play` は**対になる相手がそもそも存在しない**(`mw_core::Command` 側にも
  `BgmPause` / `BgmResumeAt` 等の variant が無い)。
- **`state` は命名差ではなく保存先が違う** —— music は `music_clock_snapshot().state`
  (`MusicClockPublisher` の seqlock 読み)、BGM は `bgm_state()`
  (`BgmStatePublisher::read`。位置も世代も持たない。M14 により BGM にクロックが無いため)。
  `Instance::track_state` で**元の2経路へ振り分けるだけ**にし、保存の統合はしていない。
- `attempt_reopen` の `restore_music` / `restore_bgm` は挙動が本当に違う
  (music は保存位置へ seek して条件付きで再生再開、BGM は常に 0 へ seek して自動再開しない)。
  対になって見えるが**意図的な非対称**なので対象外。

### 🔴 公開 FFI の面が不変であることの裏取り(実測)

「変えていないつもり」では不十分なので、次を実測した:

1. `cargo build -p mw-ffi`(`build.rs` → csbindgen)が通ること。
2. **csbindgen が生成する `unity/Runtime/Generated/NativeMethods.g.cs` を、リファクタ前後で
   生成して `diff` したところバイト単位で同一。**
3. `csharp_abi_sync` の7本(`MwResult` / `Bus` / `MusicState` / `EventKind` / `SoundMode` /
   `StreamErrorReason` / ABI バージョン)が緑のまま。

→ **ネイティブバイナリの焼き直しは不要**(挙動不変のため利用側に届ける差分が無い)。

### 差分

📌 REFACTOR-PLAN の「~400行削減」は P1-6 単体の調査時見積もりで、共通基盤を
`handle.rs` / `result.rs` に置いたぶん**実測の純減は 85 行**。数字は実測値で置き換えた。

## ✅ M3 の Android 実機確認が通った(2026-09-04。**M3 最後の未検証項目**)

M3 は実装・テストとも完了していたが、**Android 実機では一度も動かしていなかった**。
セッション21 で APK を実機(SH-M16 / Android 11)へ入れ、ユーザーに確認してもらった。

**結果(ユーザー報告そのまま)**:

> 有線イヤホンをプレイ中に引き抜くと、一瞬止まって、スピーカーから流れると同時に
> ノーツも動き出した。おそらく正常な挙動と思われる。
> (無音時間は)まあ0.5秒くらい停止していたが、プレイ中にそんなことする時点で
> まともにゲームできてないので、今のままでいいと思いますよ。

🔴 **いちばん重要なのは「音とノーツが一緒に止まって一緒に動き出した」という観察。**
再オープンで音だけが復帰してクロックが進み続けていれば**譜面がずれる**が、そうならなかった
= `Instance::restore_music` が `clock_before`(`MusicClockSnapshot`)から位置を復元する経路が
**実機で正しく効いている**。M3 でいちばん壊れやすい所がここだった。

✅ **体感の無音時間 約0.5秒はユーザー判断で許容された。**
→ 再オープンのバックオフ等の【仮】定数は、**この端末・この経路(有線引き抜き)については
実地で妥当と確認された**扱いにしてよい。

### Bluetooth も同日に確認した —— ただし「再オープンが動いた」とは書けない

> ワイヤレスイヤホンも試しました。こっちは**停止なく、スムーズに出力が切り替わりました**ね。
> まあプレイ中に切り替えることは想定していないので、ここら辺は無視でいいです。

**両経路とも実用上問題なし。M3 の Android 実機確認は完了。**

⚠️ **しかし「BT でも再オープンが動いた」とは書けない。** 無音がゼロだったということは、
Android 側が AAudio の切断イベントを出さずに**ルート変更だけで処理し、M3 の再オープン
コードがそもそも走っていない**可能性がある(有線の 0.5秒 は明確に再オープンが走った形)。
どちらなのかは logcat を取らないと分からないが、**実害が無いのでこれ以上は調べない**
(ユーザー判断「ここら辺は無視でいい」)。

🔴 **将来 BT 経路で再オープンが必要になる状況が出てきたら、まず「切断イベントが来ているか」
から確認すること。** 「BT は動作確認済み」を根拠に再オープン側を疑わない、をやらない
——このリポジトリは「安全網が別の未検証の前提に乗っている」を過去に3回連続で踏んでいる。

📌 **これで M5(ハードニング)の着手条件が揃った** —— M5 を保留していた理由は
「実機未検証の【仮】定数が複数残っている / 残る条件は Android 切断復旧の実機結果だけ」
だった(ワークスペースの `docs/HANDOFF.md`)。**保留の理由はもう無い。**
